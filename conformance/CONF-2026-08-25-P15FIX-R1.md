## OQGF-M-14 — chain freshness / no replay (F-29)

> "Intent Provenance Chains SHALL carry a freshness nonce and an expiry."

| Field | Content |
|---|---|
| Code path | The 13-FIX replay ledger consumed a `(principal, nonce)` within its expiry; 14-FIX F-13 bounded it, evicting the smallest-expiry entry at capacity. 15C F-29 showed that evicting a still-*fresh* entry opens a replay window under nonce-space exhaustion. **F-29 fix** (`check_guards`): only *expired* entries are evicted (the `retain(now <= expiry)` already ran); a ledger still full of valid nonces **rejects** the new chain ("nonce ledger full") rather than dropping a fresh one. A fresh nonce is never evicted, so it can never be replayed. |
| Test | `redteam_15c::g2_2_4_nonce_flood_no_longer_opens_a_replay_window` (fails without the fix — the "ledger full" path does not exist pre-fix, and the flood evicted the target). |
| Verdict | **strengthened.** Replay protection for a fresh nonce is now unconditional; the F-13 memory bound is preserved (the ledger never exceeds the cap) without the replay-window regression. |

## OQGF-P-1 — host-harm bound / availability (F-29 tradeoff)

> "Disruption of a legitimate operation is a governance failure of equal standing to a missed threat."

| Field | Content |
|---|---|
| Code path | The F-29 fix trades *availability under an adversarial flood* (a ledger full of `MAX_NONCE_ENTRIES = 10_000` unexpired nonces rejects further chains) for replay protection. This is bounded and correct: expired entries are always evicted first, so the ledger only fills under a genuine flood of 10⁴ concurrently-valid distinct chains — an adversarial condition the operator is meant to see and investigate, not a normal-load denial. Legitimate single-actor operation is unaffected (its nonces expire and evict on schedule). |
| Test | `g2_2_4_...` observes the "ledger full" rejection only after 10⁴ distinct fresh nonces; the existing replay/rate/monotonic tests (redteam_fix) show normal load is admitted. |
| Verdict | **satisfied.** The fix does not over-deny under legitimate load; the denial arises only under a flood, which is the correct direction (a security event surfaced, not legitimate work blocked). |
