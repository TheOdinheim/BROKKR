## 0. What was checked, against what (Section 5.3 — this is not a zero-findings assertion)

The requirements below were read from the corpus. For each, this check names the
`brokkr-core` type/function that carries it (or states that none does), the test that
proves it (or that none exists), and a verdict. The subject is the built crate; the
architecture's traceability table was **not** the enumeration source.

**Phase-1 verdict semantics** (stated so the DAP does not misread the `partial`
rows). `brokkr-core` is the *type layer*, built spine-first — types now, running
enforcement in each subsystem's own later phase. Accordingly:

- **satisfied** — the requirement's *Phase-1* obligation is fully met here: an
  invariant that lives in core is enforced by construction and proven by a test, or a
  structural encoding is complete. Nothing about it is deferred.
- **partial** — core carries the correct *type shape*, and the *running enforcement*
  is deliberately in a named later phase. This is a scoping statement, **not a
  deficiency**: it is what spine-first means. Each such row names the phase that
  closes it.
- **n.a.** — not a `brokkr-core` type at all; it lands in another crate. Names that
  crate/phase.
- **absent** — no hook, and there should be one. That is a Section 4 gap and the
  build stops. **There are none.**

Evidence is independently openable: every test named below runs under
`cargo test -p brokkr-core` (11 runtime tests + 9 compile-fail doctests, all
passing); every type named is at the cited path.

## 4. Honesty notes (Section 7)

- **No coverage or completeness claim.** This states what was checked (the corpus
  requirements whose type shape is in-scope for `brokkr-core`) and against what (the
  built crate). A `satisfied` verdict means the Phase-1 obligation is met and tested;
  it does **not** claim the eventual running system is correct — later phases prove
  their own logic at their own conformance gates.
- **Independent ground truth.** Requirements were quoted from the corpus, not from
  the architecture's traceability table. The tests use a **mock** signer/verifier/
  hasher (no wolfCrypt), so the negative tests do not validate the crate against its
  own future crypto.
- **The `no_std` claim is bounded.** It rests on `#![no_std]` compiling (any `std`
  reference would fail); a bare-metal cross-target build was **not** run because no
  such target is installed and installing is out of Phase-1 scope.
