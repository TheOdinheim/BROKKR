## 1. What this revision does and why

Phase 4 (SINDRI) must verify an Intent Provenance Chain it did **not** sign, using **public
keys** resolved from OQGF-M-1 attestations — not the signer's `DualKeyPair`. Phase 3 shipped
`Skuld::verify_chain`, which takes `DualKeyPair`s, so it can only demonstrate
*signer-verifies-own-signature*. The Phase 2 revision (`CONF-2026-07-17-P2-REV-R1`) added the
missing `DualPublicKey` type to `brokkr-crypto`. This revision **consumes** that type on the
SKULD side, adding a public-key chain verifier so Phase 4 has a SKULD-side path to call.

This is a **prerequisite for Phase 4, not Phase 4.** No gate (SINDRI) is built here.

## 2. What changed

**One production file — `brokkr-intent/src/skuld.rs`:**

- **Imports:** added `CryptoError` (from `brokkr_core::crypto`) and `DualPublicKey` (from
  `brokkr_crypto`).
- **A private trait `DualVerify`** (`fn verify_dual(&self, msg, sig) -> Result<(), CryptoError>`),
  impl'd for `DualKeyPair` and `DualPublicKey` as one-line forwards to each type's inherent
  `verify_dual`. **Private to the crate** — not `pub`, not re-exported from `lib.rs`.
- **Two shared helpers:** `check_root_signature<V: DualVerify>` and
  `verify_chain_with<V: DualVerify>` — the single place the freshness → root-sig → per-hop
  (hash-link, subset re-check, entry-sig) → advance walk lives.
- **`verify_chain` and `verify_root` now delegate** to those helpers. Their signatures and
  semantics are **unchanged**.
- **New: `verify_chain_public`** (root + hops as `DualPublicKey`) and **`verify_root_public`**,
  delegating to the same shared walk. Identical semantics, error variants, order, and
  fail-closed behavior — only the verifying-key type differs.

**One new test file — `brokkr-intent/tests/chain_public.rs`:** 6 tests (§4), real backend.

Nothing else changed. `brokkr-core`, `brokkr-crypto`, and `governance/` are untouched.

## 3. Design decision: the shared walk (preferred path taken)

The task offered a preferred path (one shared generic walk over a private `DualVerify` trait)
and a fallback (duplicate the walk byte-identically if the borrow checker fights). **The
preferred path was taken and it compiled cleanly** — the helper is generic over `V`, takes
`root_verifier: &V` and `hop_verifiers: &[&V]`, so `V = DualKeyPair` and `V = DualPublicKey`
both resolve without lifetime friction. The two inherent `verify_dual` signatures are identical
modulo receiver, and the trait impls call the inherent method by `Type::method(self, …)` (which
takes precedence over the trait method — no recursion). Because a single walk serves both paths,
the keypair and public-key verifiers **cannot drift**: same error variants, same order, same
freshness gate. The fallback (and its sync-comment obligation) was therefore unnecessary.
