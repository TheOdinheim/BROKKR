## 1. The instruction's two premises, checked against the source

Evidence is the file, not a summary (§7). Both were verified by `grep` over all of
`brokkr-core/src/` and a full read of `classification.rs`.

### Premise 1 — "classification.rs ALREADY has `Classification { sensitivity: Sensitivity, personal: bool }`"

**False.** `brokkr-core/src/classification.rs:10` is:

```rust
pub enum Classification { Public, Internal, Cui, Secret }
```

A plain tier **enum**. Sweep results:
- `grep -rn "Sensitivity" brokkr-core/src/` → **NONE**
- `grep -rn "personal" brokkr-core/src/` → **NONE**

There is no `Sensitivity` type and no `personal` field anywhere in the crate. Personal-ness
is **not** representable today. This matches what the delta R1 reported (P-11.1 → bucket B),
and it means the "correction to bucket A" rests on a shape that is not present.

Why the mismatch is expected: AMD-009 (15 July) postdates Phase 1 (14 July). At Phase 1
there was no personal-data requirement, so `Classification` was correctly a tier-only enum.
No step since has refactored it to a struct-with-`personal`.

### Premise 2 — "Accept HOLDS the existing brokkr-core `RiskAcceptance` type … Confirmed present"

**False.** `grep -rn "RiskAcceptance" brokkr-core/src/` returns only:
- `ids.rs:23` — the id newtype `RiskAcceptanceId`
- `barrier.rs:5,46` — `BarrierVerdict::AcceptedRisk { entry: RiskAcceptanceId }`

There is **no `RiskAcceptance` struct**. The AMD-006 field types it would need (`FindingId`,
`DeterministicGateId`) are also absent (`grep` → NONE).

This is not new information — it is exactly what `gaps/GAP-2026-07-15-001.md` §2–§3 filed:
*"core has only `RiskAcceptanceId` … the `RiskAcceptance` struct must enter `brokkr-core`."*
The DAP's delta review said "the verdict stands," which endorses that gap; the "Confirmed
present" in the build instruction contradicts it. The tree confirms the gap: **absent.**

## 2. Why this blocks the build (I cannot honor the constraints and build the types)

- **`Disposition::Accept { acceptance: RiskAcceptance }` cannot compile** without a
  `RiskAcceptance` type. The instruction says *"do not redefine it, do not duplicate it,
  reuse it"* — but there is nothing to reuse. Creating it would (a) contradict that explicit
  instruction and (b) require me to decide its exact shape (its `gate` field is
  gate-specific in AMD-006, yet AMD-008 P-10.4 applies Accept to **non-gate** risks too, so
  the shape is a real design choice, not a mechanical copy). Since `Disposition` is the spine
  of the whole risk-register family, `RiskEntry` and `RiskRegister` are blocked with it.
- **P-11.1 cannot be recorded as bucket A.** The instruction says treat it as already
  satisfied and *"leave Classification exactly as is."* Leaving the enum as-is means
  personal-ness stays unrepresentable, so P-11.1 is **not** satisfied. Recording it as "A /
  complete" would be a fabricated completion (§7, §9). I will not do that, and I will not
  reshape `Classification` (the instruction forbids it) — so P-11.1 has no faithful outcome
  without a DAP decision.

The genuinely unblocked pieces (the P-11 value types `Purpose`, `RetentionPeriod`, and the
`RiskAcceptance`-independent risk supporting types `Likelihood`/`Impact`/`RiskSource`/
`RiskId`/`TransferMechanism`/`TreatmentStatus`/`TreatmentPlan`) I have deliberately **not**
built either, so the checkpoint is one coherent decision rather than a half-built family
committed under a mistaken premise. I can build the entire set in one pass the moment the two
premises are resolved.

## 3. Recommendation — how to unblock in one reply

**Premise 2 / `RiskAcceptance`:** authorize **creating** `RiskAcceptance` in `brokkr-core`
(as GAP-2026-07-15-001 already recommended), and confirm its shape. A BROKKR-core-native
form, adapted from AMD-006 §5.1 and covering the non-gate case P-10.4 requires:

```rust
pub struct RiskAcceptance {
    pub finding: RiskAcceptanceId,     // reuse the existing id as the finding handle
    pub gate: Option<DeterministicGateId>, // Some(_) for a gate finding; None for a non-gate risk
    pub dap: Dap,                      // existing
    pub justification: String,
    pub expiry: Timestamp,             // existing
    pub signature: DualSignature,      // existing
}
```

This pulls in one new supporting type, `DeterministicGateId` (a small enum:
`GenomeGate` | `MhcGate`, per OQGF-G-4 / OQGF-M-1). Confirm this shape, or give me the one
you intend, and `Disposition::Accept` holds it.

**Premise 1 / personal tag:** confirm which is true —
- **(a)** the tier-only enum is intentional and personal-ness is carried *outside* core (on
  the barrier's data descriptor / BCR, Phase 6); then P-11.1 is bucket **C** and there is
  nothing to add in core (my delta R1's "B" softens to "C" — a real shrink, and the personal
  tag is genuinely not a core obligation); **or**
- **(b)** you want `Classification` to gain the personal dimension in core (e.g., a
  `personal: bool` alongside the tier, which does mean reshaping the enum into a struct —
  the reshape your instruction forbids). If (b), that reshape is an architecture change the
  DAP places, not one I make.

Either way I do **not** reshape `Classification` on my own.
