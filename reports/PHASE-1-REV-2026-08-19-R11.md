## 2. Task-by-task, with the reasoning the prompt asked for

### Task 1 — passes carry what they ran against, plus when

`SelectionPass` already carried `version: CorpusVersion`; `ScreenPass` already carried
`version: SelfSetVersion`. Neither carried a production time. Both now carry `produced_at: Timestamp`.

**ScreenPass lives in `tolerance.rs`, not `adapt.rs`** (confirmed on disk — line 151 there; adapt.rs
imports it). Its version field was already the `SelfSetVersion` §6.12 requires, so only `produced_at`
was added.

Both are documented with §6.12's rule verbatim in spirit: **version equality, not recency, is the
gate.** A pass one minute old against a superseded version is invalid; a pass a week old against the
current version is valid. `produced_at` is the audit trail — it lets `activate` flag a pass that is
version-current yet implausibly old — never the check.

### Task 2 — the evaluation-corpus content seam cannot live in core

§6.12's `EvaluationCorpusContent` is:

```rust
pub trait EvaluationCorpusContent: Send + Sync {
    fn version(&self) -> CorpusVersion;
    fn samples(&self) -> &[(Observation, Option<AttackClass>)];
    fn digest(&self) -> Digest;
}
```

`samples()` returns `(Observation, Option<AttackClass>)` pairs. **`Observation` is defined only in
`brokkr-sentinel/src/observation.rs`** — verified: `grep -rn "Observation" brokkr-core/` returns
nothing. `brokkr-core` SHALL NOT depend on `brokkr-sentinel` (**I-5**). The seam therefore cannot be
placed in core, and I placed nothing. `AttackClass` *is* a core type (adapt.rs); `Observation` is not,
and moving `Observation` into core to make the seam fit would be exactly the dependency inversion I-5
forbids.

**This is a report to Phase 9, in plain terms: `EvaluationCorpusContent` is a `brokkr-adapt`
crate-local type, placed beside its only consumer (`select`), not a core type.** A `brokkr-core` doc
note now records this so Phase 9 does not rediscover the constraint the hard way.

### Task 3 — `activate` takes `now`; `generate` and `select` do not

`activate` gained `now: Timestamp` as the **last** parameter, per §6.12 and I-13.

Reasoning for the other two, as requested — the discriminator is *does the method evaluate time*:

- **`generate`** validates that a seed is a DAP-confirmed incident and produces a candidate shell.
  It returns a `RefinedDetector`, which carries no timestamp. It evaluates no time and produces no
  time-stamped evidence. → **no `now`.**
- **`select`** measures detection improvement and coverage against a corpus, after verifying the
  corpus digest (a digest check, not a time check). Its gate is digest + measurement; the
  freshness/version gate is at `activate`, not `select`. → **no `now`.**
- **`activate`** is the one method that evaluates a pass *against the present*: it refuses a
  `SelectionPass`/`ScreenPass` whose version is not the current one, and uses `now` to flag a
  version-current but implausibly-old pass. §6.12 places `now` **explicitly and only** on `activate`
  — the architecture is meticulous about where `now` goes (see Rev 1.15's enumeration), and it did
  not route `now` through `generate` or `select`. → **`now` here.**

The `produced_at` field on the passes is *data the producing implementor stamps*; §6.12 does not
route `now` through the producing methods, and neither do I. Whether the Phase-9/Phase-8 producers
(`select`, and `ToleranceController::screen`) should receive `now` to stamp `produced_at` in the
I-13-clean way is a **producer-signature question the placed text leaves open** and that this
revision does not decide — see §4 and the recommendation. The gate that matters (version equality,
evaluated at `activate`, which has `now`) is settled.

### Task 4 — the doctest trap did not appear this time

`adapt.rs` carries **no doctests** (`grep '```' adapt.rs` → none). The I-9 negative test is an
integration test in `tests/negative_invariants.rs`, not a doctest, and no doctest anywhere in core
calls `MaturationPipeline::activate`/`select` (grep confirmed). The `activate` arity change therefore
touched no `compile_fail` annotation. Core's doctest count is unchanged (14 → 14) and all 14 pass,
which they would not if a changed type had broken a doctest. So there is no E0061-masking hazard in
this revision, and none to report a corrected code for.

## 4. The one out-of-scope consequence — a cross-scope ripple, reported not fixed

`ScreenPass` is **co-owned**: it is constructed in `brokkr-sentinel/src/heimdall.rs:406`
(HEIMDALL's `ToleranceController::screen` impl), which is **outside this revision's scope lock**.
Adding a required field to `ScreenPass` breaks that single line:

```
error[E0063]: missing field `produced_at` in initializer of `ScreenPass`
   --> brokkr-sentinel/src/heimdall.rs:406:12
```

This is the **entire** workspace break — verified exhaustively:
- `heimdall.rs:406` is the only `ScreenPass { .. }` construction outside core (grep).
- `brokkr-sentinel` does **not** touch `SelectionPass`, `activate`, or `MaturationPipeline` (grep),
  so those changes ripple nowhere.
- No other crate is affected. `brokkr-adapt` does not exist yet.

I did **not** fix it: the scope lock forbids touching `brokkr-sentinel`. Per Task 5's instruction
("a break is unexpected — investigate and report"), it is investigated and reported here. It is a
mechanical downstream consequence of a placed-architecture requirement (§6.12 mandates `ScreenPass`
carry `produced_at`), **not a framework gap** — no §4 gap is filed and the build is not stopped for it.

**Recommendation to the DAP.** The KVASIR core surface cannot land without a companion
`brokkr-sentinel` revision, because `ScreenPass` is co-owned by HEIMDALL (Phase 8). That companion
revision must (a) stamp `produced_at` at `heimdall.rs:406`, and (b) decide the open producer-signature
question from §2/Task 3: whether `ToleranceController::screen` (and, at Phase 9, `select`) should
receive `now` as a call parameter to stamp `produced_at` in the I-13-clean way, or stamp it from
another source. That is a Phase-8 trait-shape decision I deliberately did not make here — §6.12 places
`now` only on `activate`, and inventing a `screen` signature change from inside a KVASIR core revision
would be reaching past the placed text and past scope. It is flagged for the DAP to place as its own
reviewed change, consistent with the three-commit discipline (§5.2).
