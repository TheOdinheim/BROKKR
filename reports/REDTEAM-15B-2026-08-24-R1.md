## 3. Findings (F-26 … F-28)

### F-26 (LOW) — the F-22 reason-string oracle enumerates the entire genome
**Where:** `Orchestrator::execute_hop` — a genome refusal returns `reason: refusal.detail` (`lib.rs:501`), a SINDRI denial returns `"architectural anergy: {reason:?}"` (`lib.rs:525`).
**What:** 15A's F-22 established that the two reasons are *distinguishable*. 15B quantifies the impact: an attacker probing tool names classifies each as declared or undeclared **with perfect accuracy** from the reason string alone, under production guards, recovering the whole closed vocabulary. This is the concrete escalation of F-22 — not a 1-bit leak but a full map — and it strengthens the case for the F-22 fix (a uniform reason string for genome refusals, the truth retained in SAGA).
**Why LOW:** the genome vocabulary is a list of *tool names*, not a secret key; enumeration yields reconnaissance, not authority (the attacker still cannot run an undeclared, out-of-scope, or invariant-violating tool). But it defeats F-5's stated intent (hide declaration status) completely, so it is a real, named gap. **Recommendation:** fold into the F-22 fix — uniform the genome-refusal reason under `uniform_denial_stage`.

### F-27 (INFO) — `ToolOutcome.output` is an unvalidated trust boundary
**Where:** `ToolExecutor::execute` → `ToolOutcome.output` → `HopResult::Executed { output }`.
**What:** the spine does not inspect, constrain, or classify a tool's output. A malicious tool can encode anything it can see (its action detail, and any state it independently reads) into `output`, which flows to whoever consumes `HopResult`. This is a covert/exfiltration channel *from the tool to the caller*. It is inherent — a tool's job is to produce data — and the governed boundary is the *input* side (the authorized action, the barrier), not the output. **Named because a grey hat correctly identifies the output as ungoverned.** **Recommendation:** treat tool output as untrusted at the consumer; if outputs ever cross a classified boundary, route them through HÚÐ egress (they are not, today — output returns to the trusted driver).

### F-28 (INFO) — tool filesystem *reads* are unrestricted
**Where:** `brokkr-tools` — `SandboxedTool` validates *write* targets against a lexical sandbox root (13-FIX F-2); nothing restricts a tool implementation's *reads*.
**What:** a malicious `ToolExecutor` may read any path the process can (e.g., a file-backed SAGA, on-disk key material, `/etc`). In the current build SAGA is in-memory and there is no on-disk audit state, so there is no exfiltration path *today* — but the boundary is operational, not enforced. **Named as a deployment boundary**, consistent with 15A's F-24 (the tool layer is trusted-by-wiring). **Recommendation:** for production, run tools under an OS-level sandbox (seccomp/namespaces/read-only mounts) — the type system governs authority, not ambient filesystem access.

## 5. Confirmed-sound against targeted inference (the grey-hat "PASS" list)

- **Enumeration ≠ authority.** F-26 maps the vocabulary; the attacker still cannot run an undeclared, out-of-scope, or invariant-violating tool (every path denies, `combined_3_1`).
