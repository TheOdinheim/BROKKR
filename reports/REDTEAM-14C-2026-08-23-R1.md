## 1. Summary

All confirmed. 0 critical, 0 high.** Four findings (F-18…F-21): one informational asymmetry, two LOW (an unbounded-read DoS and a HEIMDALL reconciliation gap on tool failure), one informational timing side channel — all safe or bounded, none admitting an unauthorized action.

| Category | Result |
|---|---|
| 1. `unsafe` memory safety | **sound** — `Drop` never sees null; buffers dynamically sized or correct-constant; all FFI key types `Drop` (no partial-keygen leak); one info asymmetry (F-18) and one LOW DoS (F-19) |

The timing side channels are real and inherent — documented, not fixable without constant-time crypto the threat model does not require (the observer must be the *trusted driver*, not the model).

## 2. Per-category results

### Category 1 — `unsafe` memory safety (code reading)

| # | Attack | Finding |
|---|---|---|
| 1.1 | `TlsClient::Drop` with null pointers | **safe** — `TlsClient { ssl, ctx }` is constructed only *after* `wolfSSL_connect` succeeds (tls.rs:229); every earlier failure returns `Err` via `free_ctx_err`/`free_ssl_ctx_err` without building the struct. `Drop` never sees null. (And `wolfSSL_free(NULL)` is a no-op — defense in depth.) |
| 1.2 | `write_all` `c_int` truncation | **safe** — `remaining.len().min(c_int::MAX as usize) as c_int`: the `.min()` guarantees the value is ≤ `i32::MAX` before the cast, so the cast never truncates. Watertight. |
| 1.3 | `read_until_close` unbounded allocation | **LOW — F-19.** No size cap; `out` grows until the peer closes or errors. |
| 1.4 | ffi.rs buffer sizes vs NIST | **safe** — signature buffers are **dynamically sized** via `self.sig_size()?` (queried from wolfCrypt), so an undersized-SLH-DSA-sig overflow is impossible; the `sig_len` capacity is passed to the library so it writes ≤ capacity. Public-key constants are the correct NIST sizes: `MLDSA65_PUB_SIZE=1952`, `SLHDSA192S_PUB_SIZE=48`. |
| 1.5 | `DualKeyPair::generate` partial-failure leak | **safe** — **every** FFI key type impls `Drop` (`MlDsa65`→`wc_MlDsaKey_Delete`, `SlhDsaShake192s`→`wc_SlhDsaKey_Free`, `Rng`→`wc_rng_free`, …). If ML-DSA generates and SLH-DSA then fails, `?` returns and the ML-DSA key's `Drop` frees it — no leak. |

**F-18 (INFORMATIONAL) — the SLH-DSA signer has no signature-size cross-check.** `MlDsa65::generate` guards against a wrong-parameter key with `if me.sig_size()? != MLDSA65_SIG_SIZE { return Err(-2) }` (ffi.rs:392); `SlhDsaShake192s::generate` has **no** analogous `sig_size() == constant` assertion. This is **not** a memory-safety issue — the SLH-DSA sign buffer is sized from `sig_size()` itself, so it always fits — but it is a defense-in-depth asymmetry: the ML-DSA path detects a mis-parameterized key at construction; the SLH-DSA path trusts the library. **Recommendation (optional):** add a `sig_size()` sanity check to `SlhDsaShake192s::generate` symmetric with ML-DSA, so a wrong SLH-DSA parameter set is caught at keygen rather than trusted.

**F-19 (LOW) — `TlsClient::read_until_close` allocates unbounded.** `out.extend_from_slice(...)` in a loop with no size cap: a malicious or compromised endpoint that streams data without closing can drive the client to OOM. **Why LOW:** the endpoint is a **mTLS-authenticated, REGIN-registered, DAP-owned** gateway (not an arbitrary attacker), and the read runs on the caller's own thread (a self-inflicted DoS at worst). **Recommendation:** cap `out` at a configured maximum (e.g. a few MiB — an ollama coding response is small) and return `TlsError` past it.

### Category 2 — integer / cast safety (code reading)

| # | Attack | Finding |
|---|---|---|
| 2.1 | `check_guards` timestamp arithmetic | **safe** — `now.0.saturating_sub(rl.window_ms)` cannot underflow; no other wrapping/panicking arithmetic in the guard logic |
| 2.2 | SAGA sequence `u64` overflow | **safe-by-bound** — `seq = records.len() as u64`; overflow needs `u64::MAX` records (≈1.8×10¹⁹), unreachable before storage exhaustion. Documented. |
| 2.3 | rate `len() as u32` wrap | **safe-by-bound** — needs `> u32::MAX` hops within one window; impossible in practice |
| 2.4 | `write_all` `off` overflow | **safe** — `off: usize` bounded by `data.len() ≤ isize::MAX` (a `&[u8]` cannot exceed it); `off += n as usize` with `n>0` cannot overflow |

### Category 3 — panic safety & Mutex poisoning

| # | Attack | Finding |
|---|---|---|
| 3.1 | tool panics during `execute` | **recovers** — no lock is held across `tool.execute` (`check_guards` released `guard_state`; each `audit.record` released SAGA before the tool ran), so a caught panic poisons nothing; a second hop on the same orchestrator executes (`attack_3_1`) |
| 3.2 | SAGA lock poisoning | **recovers** — both `state()` and `signer()` use `self.<lock>.lock().unwrap_or_else(\|p\| p.into_inner())`, recovering the guard on a poisoned lock rather than propagating a panic |
| 3.3 | lock ordering (guard_state ↔ SAGA; state ↔ signer) | **no deadlock** — `check_guards`'s `guard_state` guard is dropped before `audit.record` locks SAGA (never overlapping). Within SAGA, `append` is the *only* method holding both locks (order **state→signer**); `export` releases `state` before taking `signer`; no method takes `signer→state`. No inversion. |
| 3.4 | concurrent panic + normal path | **isolated** — a panicking hop in one thread does not corrupt a normal hop in another (Rust panics are per-thread); the normal hop completes (`attack_3_4`) |

### Category 4 — timing side channels (runtime, informational)

| # | Attack | Measured | Finding |
|---|---|---|---|
| 4.1 | Signal-1 vs Signal-2 denial latency | Signal-1 (identity lookup) **≈1.6 µs**; Signal-2 (dual-family verify) **≈4.19 ms** — **~2600×** | **F-21** |
| 4.2 | guard vs SINDRI denial latency | replay-guard denial **≈10 µs**; SINDRI crypto grant **≈4.31 ms** — **~415×** | **F-21** |

**F-21 (INFORMATIONAL) — evaluation time leaks the failing stage.** An observer who can time `execute_hop`/`evaluate` can distinguish (a) a wrong *identity* (fast lookup) from a wrong *signature* (slow crypto), and (b) a *guard* denial (replay/rate, no crypto) from a hop that *reached the gate*. **Why informational, not a defect:** the timing difference is inherent in doing variable-cost work (a signature verification *is* ~1000× a hashmap lookup), and closing it would require constant-time evaluation the threat model does not demand — crucially, the party who can time the orchestrator is the **trusted driver** that *calls* `execute_hop`, **not** the untrusted model (which only emits a `Proposal` and never sees latency or the `HopResult`). The leak is to a party that already knows the inputs. **Recommendation (only if `HopResult` is ever exposed to a less-trusted caller):** a fixed floor delay on denials, or evaluate all conjuncts before returning. Not warranted today.

### Category 5 — cross-subsystem interaction (runtime)

| # | Attack | Finding |
|---|---|---|
| 5.1 | HEIMDALL observation after a tool **failure** | **F-20** — a `tool.execute` `Err` returns `HopResult::Error` *before* the step-8 reconciliation feed, so **no `Observation::Hop` is emitted**; a failed authorized execution is invisible to HEIMDALL's behavioral loop |
| 5.2 | SAGA has a Proposal but SINDRI denies | **consistent** — the audit shows **Proposal → anergic Authorization** (both recorded); you learn what was proposed even when it was rejected; the tool never ran (`attack_5_2`) |
| 5.3 | BIFRÖST deny records to SAGA; model never called | **correct (I-12)** — a `BarrierCrossing` denial is recorded and the reasoner call count is **0**; the classified context stays within the boundary (`attack_5_3`) |

**F-20 (LOW) — a tool execution failure is invisible to HEIMDALL.** In `execute_hop`, `tool.execute() → Err` returns `HopResult::Error` at step 7, *before* the step-8 `sentinel.observe(Observation::Hop { executed: Some(..) })`. So HEIMDALL's cross-hop reconciliation never learns that an *authorized* action *failed to execute*. **Why LOW:** the failure is surfaced to the caller (`HopResult::Error`) and, in production, the driver records it; but HEIMDALL cannot detect a *pattern* of authorized-but-failing tools (e.g. a tool consistently erroring after authorization — a possible tamper or resource signal). **Recommendation:** emit an observation on tool failure — either `Observation::Hop { authorized, executed: None }` (reusing the "no execution" shape) or a dedicated failure observation — so HEIMDALL's behavioral loop sees execution failures. A reconciliation-completeness improvement, not a safety hole.

## 3. Confirmed-sound internals (the white-box "PASS" list)

- **Memory safety:** `TlsClient` never holds null pointers; signature buffers are library-sized; pubkey constants are correct; every FFI key type frees itself on drop (no leak on partial keygen); the write cast is `.min()`-bounded.
- **Arithmetic:** every guard/buffer operation is `saturating`/`.min()`-bounded or bounded by `isize::MAX`; no exploitable overflow.
- **Panic/poison:** no lock is held across the tool call; both SAGA locks recover from poison; the only dual-lock method (`append`) has a consistent order; panics are per-thread.
- **Interaction:** the audit trail is consistent across every deny path (Proposal→Denied, BarrierCrossing on crossing-deny); I-12 holds (model never called on a crossing deny).

## 4. Findings summary (F-18 … F-21)

| ID | Sev | What | Fix direction |
|---|---|---|---|

| F-19 | LOW | `read_until_close` unbounded allocation (DoS via infinite stream) | cap the response size |
| F-20 | LOW | tool execution failure emits no HEIMDALL observation | observe on failure too |

None is a memory-safety or authorization defect. All four are documented with a concrete (optional) hardening.

## 5. Scope honesty — and the close of the red-team campaign

Low-noise white box, the deepest layer. Not covered, and honestly out of scope for hand-written adversarial tests: a **formal** proof of the wolfCrypt FFI's soundness against the exact linked `libwolfssl.so.45` (that requires the library's own verification, which BROKKR treats as a trusted, version-pinned dependency per the FFI honesty rule), and **fuzzing** the TLS read loop / JSON extractor (this campaign used adversarial hand-picked inputs, not a fuzzer).

**Across the whole red-team campaign (13A–13C black box, 14A–14C white box): ~130 attack vectors, 0 unauthorized executions, 0 memory-safety defects, 0 panics that abort.** The findings are F-1…F-21: ten black-box findings all *hardened* in 13-FIX, and eleven white/deep findings that are informational or LOW, each named with a concrete hardening. The structural guarantees hold; the logic behind them is sound; the internals are memory- and panic-safe. The residual attack surface is exactly what the architecture already names in §13 — the tool layer, the audit-render layer, and the model's own competence — plus the four small defense-in-depth items above.
