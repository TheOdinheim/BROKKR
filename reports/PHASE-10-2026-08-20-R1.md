## 2. The three Step-0 readings

**(a) What `brokkr-reasoner` contains — a `ModelBackend` seam.** BROKKR has no model of its own (I-6), so the model call is a **seam**: a `ModelBackend` trait injected into `Mimir` at construction. Its signature *is* the structural guarantee of two of §6.1's binding rules:

```rust
pub trait ModelBackend: Send + Sync {
    fn propose(&self, payload: &str, scope: &IntentScope) -> Result<BackendProposal, BackendError>;
}
pub struct BackendProposal { pub action: Action, pub rationale: String }
```

The backend receives the cleared **payload** (`&str`) and the **current attenuated scope** — **not** the `ClearedContext` (a governance token; the model gets text, not authority), and **no channel to any gate** (it returns only an `Action` + rationale — no `AuthorizedAction`, no `BarrierVerdict`, no boolean a rationale could flip). Phase 10 supplies test-double backends; a production backend (the real network call, through BIFRÖST) is a deployment concern.

**(b) What `brokkr-tools` contains — a `ToolExecutor` trait + stubs.** No architecture section describes it, but the minimum viable shape is buildable from committed types and needs **no** invented governance, so no gap:

```rust
pub trait ToolExecutor: Send + Sync {
    fn tool_id(&self) -> &ToolId;
    fn execute(&self, action: &AuthorizedAction) -> Result<ToolOutcome, ToolError>;
}
```

A tool executes an **already-authorized** action — SINDRI minted the `AuthorizedAction` (I-1); the tool does not re-check and *cannot* (the mint is sealed in `brokkr-core::gate`). `ToolSchema` is opaque prose, so dispatch is by `ToolId` (the executor's job, Phase 11), not by a structured schema. Stubs: `NoOpTool`, `FixedResultTool`.

**(c) Dependency directions.** `brokkr-tools` depends on `brokkr-core` only. `brokkr-reasoner` depends on `brokkr-core` and `brokkr-bifrost`. **Neither depends on the other** — a `Proposal` names an `Action`/`ToolId`; a tool receives an `AuthorizedAction`; the connection is the executor (Phase 11). `cargo tree` confirms the trees, and **no crate depends on either** (I-5).

*Honest nuance, reported:* the `Reasoner` trait impl itself uses only `brokkr-core` — `ClearedContext` is a **core** type that `propose` *receives* (it does not mint one; BIFRÖST does). The `brokkr-bifrost` regular-dependency edge (per scope) establishes I-6 (the reasoner is the crate whose production model channel goes through BIFRÖST) and is **exercised end-to-end** in `tests/mimir.rs` (a real `Bifrost` clears a context before MÍMIR proposes on it), so the dependency is genuine rather than nominal.

## 3. The three §6.1 binding rules — all structural

1. **Model receives only the current attenuated scope** — `propose` forwards the `&IntentScope` argument; MÍMIR never holds the root intent.
2. **No channel to a gate** — `ModelBackend::propose` returns only a `BackendProposal`; there is no gate in the interface.
3. **Endpoint registered** — checked in `Mimir::new` against the `RegisteredEndpoints` seam; an unregistered endpoint yields `ReasonerError::UnregisteredEndpoint` (construction-time, so a MÍMIR against an unregistered endpoint cannot exist). The seam is backed by REGIN's signed `EndpointRegistry` in production (Phase 11); a test double serves the tests.
