## 3. Why the build stopped (detail in `GAP-2026-07-27-001`)

§6.2 predicate 5 ("a `ToolEntry` names a capability the intent vocabulary does not recognize") needs
a committed set of recognized capabilities to be a *fireable* check. None exists:

- `Capability` is `Capability(pub String)` — an open newtype; the type recognizes every string.
- No register enumerates valid capabilities (the six are tools, cbom, aibom, endpoints, roots,
  policy).
- The only derivable capability set is the union of `ToolEntry.required_capabilities`; checking the
  tools against the set the tools define is **vacuous** — a predicate that can never fire, which
  §6.2's own predicate 6 (line 434) calls "worse than absent."

So predicate 5 is either uncomputable (no master list) or the dead predicate §6.2 forbids. Building
it requires inventing a vocabulary source — forbidden by §4 and the phase instruction ("do not
resolve it by picking the reading that compiles"). The asymmetry with predicate 6 is the tell:
predicate 6 works because it checks *policy* capabilities against a real committed set (the
tool-union); predicate 5 has no external set to check *tool* capabilities against.

## 4. Checkpoint reporting items the prompt required (recorded here even though no crate was built)

The prompt asked the phase report to include four specific determinations. I made them during the
design that preceded the stop; recording them so the DAP can ratify them alongside the gap
disposition, and so the build is fast afterward:

- **Task 3 — verdict-type placement:** the `PromotionVerdict` belongs in **`brokkr-genome`**, not
  `brokkr-core`. Reason: unlike `BarrierVerdict`/`AuthorizedAction`, **no core trait returns it** —
  the promotion gate is REGIN's function, produced by `brokkr-genome` and consumed by the release
  pipeline (Phase 11); it is not cross-cutting vocabulary like `Classification`. Placing it in core
  would be a core revision (a separate DAP-reviewed commit), which this phase must not do. The
  I-2/OQGF-P-2 no-downgrade discipline is a property I encode wherever the type lives; it does not
  require core residence. **I do not judge it belongs in core, so I do not stop on Task 3.**
- **Self-Set screening (OQGF-P-3) — excluded, per instruction.** The architecture's crate comment
  mentions REGIN is "simultaneously the Self Set." CLAUDE.md §5.1's Phase-5 scope line does **not**
  list Self-Set screening, and screening applies to heuristic detectors that do not exist until
  Phases 8–9. **Excluded from Phase 5**, as the prompt directs.
- **Genome signature covers register signatures — the chosen encoding.** The genome's signed content
  will cover `version`, `corpus_digest`, `owner`, and **each register's FULL canonical bytes
  *including* that register's own signature** — so the genome signature commits to *which signed
  registers it was assembled from* (swapping in a differently-signed register breaks the genome
  signature). Each register's *own* signed content excludes only that register's own signature.
  This is the intended design; it lands when the build proceeds.
- **Non-suppressibility — the structural finding.** The promotion gate is unaddressable by a
  `ToleranceGrant` because a grant targets a `DetectorId` and the gate has none (§2). This is *why*
  it is non-suppressible, stated as a verified fact, not an assertion. It will be reflected in the
  no-downgrade `PromotionVerdict` (no `Blocked → Promoted` path, mirroring `BarrierVerdict`'s I-2).
