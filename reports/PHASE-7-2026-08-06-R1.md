### 2.4 The no-resurrection half of Task 4 is structurally clean (recorded, not blocked)

Separately from the linkage contradiction: §6.9 lines 958 requires re-signing to **not** resurrect
erased data — the re-signer operates over the record's canonical bytes and ciphertext only, holds no
subject key, and has no decrypt path. This is buildable and enforceable by type signatures: the
re-signer's input is the record's already-serialized bytes plus a `DualKeyPair` to sign with; it is
never handed a `SubjectKey` (the only type with `unwrap_data_key`/`shred`), so the *type* of the
re-signing function makes decryption unrepresentable — the same structural device as `AuthorizedAction`.
This half does not depend on the linkage definition and is not part of the gap. The blocked half of
Task 4 is solely "re-signing preserves the chain," which requires the linkage digest §3 concerns.

## 3. Why the build stopped — the §6.9 chain-linkage contradiction (GAP-2026-08-06-001)

The prompt required me to resolve, decide, and report the interaction the Task 4 note calls "the
subtlest thing in the phase" — that appending a signature changes the FULL bytes the next record's
`prev` digests — **unless the tension is genuine, in which case STOP and file a gap.** It is genuine.

§6.9 states three things; any two hold, not all three:

- **(a)** `prev` = digest of the preceding record's "full canonical bytes, **including its signatures**"
  (lines 918–919, 937–939), and "an entry cannot be altered after the fact without breaking every link
  after it."
- **(b)** Re-signing **appends** a `GenerationSignature` (line 956) — `signatures` grows.
- **(c)** Re-signing leaves "the chain through it **unchanged**" (line 956); OQGF-A-6: "preserving the
  original signatures **and chain**."

(a)+(b) ⇒ appending a signature to record *N* changes *N*'s full-bytes-including-signatures ⇒ changes
what *N+1*'s `prev` digested ⇒ **breaks the link**, by (a)'s own words. That contradicts (c). It is the
same "SAGA reports its own compliance action as an integrity attack" failure §6.9 resolves for erasure
(never delete) but leaves standing for re-signing. The prompt's Task 1 definition — full bytes =
"signed content + **all accumulated** signatures", "the full bytes are what the next record's `prev`
digests" — is the collision made explicit. (`timestamping` has the same shape: a token is attached
*after* signing, so if full bytes include it, the first timestamp attachment mutates an already-linked
record too.)

The two resolutions available to me are each forbidden by §4:

- **B — linkage over SIGNED CONTENT only.** Resolves it cleanly and is defensible (signatures verified
  independently against signed content; content tampering caught by the linkage digest). **But it
  contradicts §6.9's explicit "including signatures."** Adopting it silently = building against the
  read-only architecture text and choosing the reading that unblocks me.
- **C — freeze the linkage digest at the original signature.** Makes all three statements literally
  true. **But §6.9 nowhere states "first-signature-only";** a faithful implementer digests the current
  `signatures` vec and the chain breaks. Adopting it = inventing the unstated convention.

Neither is mine to adopt. The chain-linkage digest is the spine — Tasks 1, 3, 4 and the two most
load-bearing tests (`test_oqgf_p_11_5_erasure_preserves_chain`,
`test_oqgf_p_11_7_resigned_erased_record_stays_irrecoverable`) all turn on it — so the whole phase stops,
not "build the rest and gap the chain." Full analysis and recommendation: **GAP-2026-08-06-001**.

## 4. The two Step-0 readings the prompt required — resolved (neither is a blocker)

**(4a) `AuthorizedAction` cannot be held by an `AuditEvent`; the authorization event records the
`Action` + the decision.** Confirmed against `gate.rs`: `AuthorizedAction` has a private `action` field,
no public constructor (minted only inside `CostimulationGate::authorize`), and derives **neither `Clone`
nor `Copy`** — so it cannot be stored in, or copied into, an event. What it *proves* is recorded instead:
the authorization event carries the `Action` (obtained via `AuthorizedAction::action() -> &Action`, and
`Action` derives `Clone`) together with the decision outcome — `Granted`, or `Anergy { reason:
AnergyReason }` (`AnergyReason` derives `Copy`). This records what the gate decided and over which action,
which is the accountable fact, without the impossible move of storing the capability token itself. The
`AuthorizedAction` type keeps its I-1 property (unforgeable, one-shot) untouched; SAGA records its
*shadow*, not the token.

**(4b) `RiskRegister::record(&self, ..)` takes `&self` ⇒ interior mutability; `brokkr-audit` is a `std`
crate.** Confirmed against `risk.rs`: `record(&self, RiskEntry) -> RiskId` and `inventory(&self) ->
Vec<RiskEntry>` both take `&self`, so an append-only implementor cannot use `&mut self` and must hold its
store behind interior mutability. `brokkr-audit` may be `std` exactly as `brokkr-barrier` is (`brokkr-core`
is the only `no_std` crate; downstream crates are `std`), so the implementation will use
`std::sync::Mutex<Vec<..>>` (or `RwLock` for read-mostly inventory) — `Send + Sync` is satisfied, and the
trait's `Send + Sync` bound is met. This is an implementation consequence §6.9 line 1017 names explicitly
("an implementor carries interior mutability; that is an implementation consequence, not a new
requirement"), not a gap.

## 5. The chain-break Signal (Task 3) — chosen class and severity (recorded for when Task 3 unblocks)

Determined now so the decision is on record, though Task 3 is blocked on §3: the A.6.1 audit-chain-break
trigger is a `Signal` from `OrganId::Audit` with **`class = SignalClass::ThreatDetected`** and
**`severity = Severity::Critical`**. Rationale: a hash-chain mismatch means the append-only record — the
system's ground truth for every other organ, including KVASIR's seeding incidents and EIR's incident
preservation — can no longer be trusted; that is a detection of a concrete integrity failure
(`ThreatDetected`, not a mere `StateChangeNotice`), and it is the most severe class of finding SAGA can
raise because everything downstream reasons over the record it just found broken (`Critical`). The
effect is `PostureEffect::Raise` (raise-only autonomy, OQGF-P-7.4 — the envelope has no `Lower`). This is
recorded as the intended construction; it is not exercised, because Task 3 is blocked.
