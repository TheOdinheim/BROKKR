## 2. What was placed (Task 1) + the dependency direction

Four fields added to `Context`, in §6.6's order: `datum: DatumRef`, `classification: Classification`,
`personal: Option<PersonalDataTag>`, `bcr: Option<BoundaryCustodyRecord>`. Docs record: **`classification`
is declared, never inferred** (inferring sensitivity from unlabeled content is OQGF-I-12 Heuristic, and a
Deterministic Gate SHALL NOT take its input from a heuristic one); **`bcr` is required above Public**
(OQGF-I-9), `None` for Public; and a struct-level doc records **why the facts ride on the context rather
than beside it** (a classification passed to `clear` separately can be passed wrongly, drift out of sync,
or come from a different caller — the same reasoning that put the personal tag on the flow in Rev 1.7).

**Imports added** (each needed): `PersonalDataTag`, `BoundaryCustodyRecord` from `crate::barrier` (the
existing `use crate::barrier::{BarrierVerdict, Destination}` is extended); `Classification` from
`crate::classification`; `DatumRef` from `crate::ids`. **No cycle:** `reasoner.rs` already imports from
`barrier.rs`, and `barrier.rs` does **not** import from `reasoner.rs` (grep-confirmed), so the direction is
one-way; `barrier.rs` is unchanged.

**Task 2 — `Context` has no constructor.** It is a plain struct with public fields, so there is nothing to
update beyond the fields themselves; the derives (`Debug, Clone, PartialEq, Eq`) still hold — every new
field's type is `Clone`/`Eq` (`DatumRef`, `Classification`, `PersonalDataTag`, `BoundaryCustodyRecord`).

## 3. Task 3 — the doctest trap, handled and verified (a real correction, not just an update)

The `E0616` compile_fail doctest constructs a `Context { .. }` inline, so Task 1 threatened to turn its
error into `E0063` (missing fields) while `compile_fail` stayed green. **Fix:** the inline `Context` is now
built in full (all five fields), so a missing-fields error is impossible. Then, as mandated, I compiled
each doctest snippet standalone against the built rlib and read the **actual** code:

| Doctest | Declared (before) | **Actual (verified by standalone compile)** | Action |
|---|---|---|---|
| `ClearedContext { inner: Context { .. } }` | `E0616` | **`E0451`** — *"field `inner` … is private"* in a **struct-literal construction** | annotation corrected `E0616` → `E0451` |
| `r.propose(&raw, scope)` (`raw: Context`) | `E0308` | **`E0308`** — *expected `&ClearedContext`, found `&Context`* | unchanged (matches) |

**The `E0616` annotation was pre-existing and wrong, and rustdoc never enforced it.** `E0616` is private-
field *access* (`value.inner`); **constructing** a struct literal with a private field is `E0451`. The
doctest has always emitted `E0451`; it passed only because `compile_fail` checks that compilation *fails*,
not the code — exactly the trap Task 3 names. The verification caught the latent mismatch, and the
annotation now states the code the compiler actually emits. **The doctest still proves I-12** — a
`ClearedContext` cannot be constructed with its private `inner` from outside the module; only `clear` mints
one. (The second doctest, `E0308`, does not construct a `Context` inline — `raw: Context` is a parameter
type — so it was untouched and re-verified.)
