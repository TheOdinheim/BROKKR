## 1. What was built

`brokkr-crypto` — hand-written wolfCrypt FFI implementing the `brokkr-core` crypto traits,
plus dual-family signing and the crypto-shred primitive. Three layers, `unsafe` in exactly
one file:

- **`src/ffi.rs`** — the **only** `unsafe` in the workspace. Raw `extern "C"` declarations
  matched to the wolfSSL v5.9.2 header prototypes, plus safe RAII wrappers. Every `unsafe`
  block carries a `// SAFETY:` comment; raw pointers/structs never escape the file.
- **`src/hash.rs`, `src/sign.rs`, `src/shred.rs`** — safe wrappers implementing the core
  traits. Each begins with `#![forbid(unsafe_code)]`. (The crate root cannot forbid
  crate-wide without also forbidding `ffi.rs`; the discipline is per-module — documented in
  `lib.rs`.)
- **`build.rs`** — link config (choice stated below).

## 3. The load-bearing finding (GAP-2026-07-16-001), flagged

**The prompt's `wc_MlDsaKey_Sign`/`_Verify` do NOT exist as exported symbols.** They are
header-only legacy wrappers; `wc_mldsa.h:704` directs new code to `wc_MlDsaKey_SignCtx()`
with ctx=NULL. I bound the exported `wc_MlDsaKey_SignCtx`/`_VerifyCtx` (same ML-DSA
algorithm, same key type), documented it in `ffi.rs`, and verified it functionally
(round-trip + tamper + 3309-byte size) and at the symbol level (`nm -u`). This is not a
wrong-algorithm substitution; it is the correct exported function per the header. Reported
rather than papered over.

## 4. `build.rs` link choice

I emit explicit `rustc-link-search` + `rustc-link-lib=wolfssl` (not `PKG_CONFIG_PATH`),
because the `.pc` files are off the pkg-config path and one verified library location is
more transparent, plus an **rpath** so `cargo test` binaries load `libwolfssl.so.45` at
runtime without `LD_LIBRARY_PATH`.

## 6. What each test proves (real crypto, not mocks)

- **SHA-384** — matches the NIST FIPS 180-4 `"abc"` known-answer vector (external truth).
- **ML-DSA-65** — sign/verify round-trip; tampered message and tampered signature both
  fail; signature is exactly 3309 B (FIPS-204 params — the not-dilithium anchor).
- **SLH-DSA-SHAKE-192s** — round-trip; tamper fails; 16224-byte signature.
- **Dual signature** — verifies only if BOTH families verify; corrupting **either** the
  ML-DSA half **or** the SLH-DSA half fails the whole. This proves dual-family (OQGF-R-1)
  is real, not two independent checks either of which could pass alone.
- **ML-KEM-768** — encapsulate/decapsulate produce the same 32-byte shared secret.
- **Crypto-shred** — wrap a random AES-256 data key under ML-KEM; unwrap round-trips; a
  *different* subject key cannot unwrap (AEAD tag rejects); **after `shred()` destroys the
  ML-KEM private key, unwrap is impossible → the data key (and data) is irrecoverable**,
  and the wrap is ML-KEM, never classical (OQGF-G-7).
