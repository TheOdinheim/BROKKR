**The load-bearing white-box result:** you cannot forge an `AuthorizedAction` or a `ClearedContext` from any crate — not by a struct literal (private field, E0451), not by calling the minter (private fn, E0624), not by `Default` (not derived, E0599), not by overriding the provided `authorize`/`clear` (the override compiles but *cannot mint*, E0624), and not by `transmute` (every non-crypto crate is `#![forbid(unsafe_code)]`, E0133). The whole `unsafe` surface is confined to `brokkr-crypto`, every operational site carries a `// SAFETY:` rationale, and the dependency graph is one-way.

**Two findings, both informational (F-11, F-12)** — precision corrections to the *task's own Step-0 claims*, where the mechanism is subtler (and stronger) than stated. Neither is a code defect.

Cloning a token is impossible.

### Category 6 — `unsafe` surface review

- **6.1 — every real `unsafe` block is in `brokkr-crypto`.** Grep across the workspace: the only files with `unsafe` *code* are `brokkr-crypto/src/ffi.rs`, `.../tls.rs`. Every other crate's match is the `#![forbid(unsafe_code)]` attribute or doc text. **All twelve non-crypto crates carry `#![forbid(unsafe_code)]`** (verified). `brokkr-crypto` correctly does **not** forbid crate-wide (it uses per-module discipline; `sign.rs`/`hash.rs`/`shred.rs` have zero `unsafe`).
- **6.2 — `tls.rs`: 12 `unsafe` sites, 12 `// SAFETY:` comments.** Each block's invariant (live `WOLFSSL`/`WOLFSSL_CTX`, valid fd, bounded slice) is upheld by the safe wrapper.
- **6.3 — `ffi.rs`: 44 `unsafe` sites; every *operational* site carries a SAFETY comment within its preceding lines.** The **one** site without an adjacent SAFETY comment is `unsafe extern "C" {` (line 80) — the raw FFI *declaration* block, which performs no operation (declaring an `extern` signature cannot cause UB; the *call sites* each carry their own SAFETY). Covered by the module-level ground-truth doc. **Not a finding.**
- **6.4 — no double-free / use-after-free via `TlsClient`.** `Drop` calls `wolfSSL_free(ssl)` then `wolfSSL_CTX_free(ctx)` **once**; Rust ownership prevents a second drop, and the borrow checker prevents use-after-drop. The `TcpStream` drops last, closing the fd wolfSSL used.
- **6.5 — no buffer overflow via `read`/`write`.** `write_all` loops over `data.get(off..)` (bounds-checked, never indexing) with the length capped at `c_int::MAX`; `read_until_close` copies only `buf.get(..n)` (bounds-checked). No unchecked indexing, no unbounded copy.

**No `unsafe` finding.** The surface is confined, commented, and the safe API exposes no path to UB.

## 3. Findings

### No critical or high findings

Every forgery attempt is a compile error; every SAGA tamper/delete is detected; the dependency graph is one-way; the `unsafe` surface is sound and confined.

### F-11 (INFORMATIONAL) — the guarantee is "private minter," not "sealed trait"

The task's Step-0 claim #3 states `authorize`/`clear` are "sealed via a private module or non-exhaustive signature." **They are not sealed.** `CostimulationGate` and `ContextClearance` are ordinary public traits, and an implementor *can* override the provided `authorize`/`clear` — the override **compiles**. The real, stronger guarantee is that **the minter (`AuthorizedAction::mint` / `ClearedContext::mint`) is module-private**, so an override written in any other crate cannot construct the token and can only ever return `Anergy` / the blocking verdict. The 2.1/2.2 doctests prove this precisely (the override body fails at `mint`, E0624). This is a documentation-accuracy note about the *task*, not a defect — and the committed doc comments already describe the mechanism correctly ("`mint` is module-private and `authorize` remains its only caller, so an override … can only ever return `Anergy`").

### F-12 (INFORMATIONAL) — `forbid(unsafe_code)` is a *crate attribute*, not inherited by a doctest

A first draft of the 1.5 transmute doctest would have **succeeded** (compiled), because a doctest is built as its own crate and does **not** inherit `brokkr-tools`'s `#![forbid(unsafe_code)]` — and `AuthorizedAction` is a same-layout newtype, so `transmute::<Action, AuthorizedAction>` is layout-valid. The transmute defense therefore rests on the **crate attribute**, verified by grep (every non-crypto crate forbids `unsafe`), not on the type alone. The doctest was corrected to carry `#![forbid(unsafe_code)]` inside itself so it demonstrates the property that actually holds in every non-crypto crate (E0133). Named because it is a genuine subtlety a white-box attacker would probe: *the private field alone is not the whole defense against transmute — the crate attribute is.*

## 4. Confirmed structural guarantees (the white-box "PASS" list)

- **I-1** — `AuthorizedAction` is unforgeable: private field (E0451), private minter (E0624), no `Default` (E0599), no `Clone`, no override path to `mint` (E0624), no transmute under `forbid` (E0133).
- **I-12** — `ClearedContext` is unforgeable by the same five mechanisms; `Reasoner::propose` takes `&ClearedContext`, so the model cannot be reached without BIFRÖST minting one (existing E0308 doctest).
- **SAGA** — append-only `&self` API, auto-assigned sequence, `records()` returns a clone, tamper/delete caught by `verify_chain` → `Broken` + chain-break `Signal`.
- **Module privacy** — every governance struct's fields are private; `mint` is private; no `#[non_exhaustive]` confusion vector.
- **I-5 / I-6** — one-way dependency graph; governance never names the untrusted side; the model's only network path is through BIFRÖST.
- **`unsafe` confinement** — the entire `unsafe` surface is `brokkr-crypto`; every operational site is SAFETY-commented; no UB reachable from a safe API.

## 5. Scope honesty

High-noise white box: **direct structural attacks** — forge a token, override a sealed method, tamper the chain, violate the dependency graph, exploit `unsafe`. The next round (14B, low noise) is where the subtle white-box attacks live: a logic error in a `SAFETY` invariant that only manifests under a specific FFI return, a `verify_chain` edge case (empty chain, single record, re-signed record), a `Drop` ordering hazard under panic, or a governance-relevant integer overflow in the guard state. This round confirms the *blatant* structural guarantees hold; it does not exhaustively prove the *absence* of a subtle logic bug behind them.
