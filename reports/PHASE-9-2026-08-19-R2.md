## 2. The three Step-0 readings

**(a) Dependency direction — brokkr-adapt DOES depend on brokkr-sentinel.** I-9's only dependency constraint on this crate is *"SHALL NOT depend on `brokkr-reasoner`."* `brokkr-sentinel` is a *governance* crate, so `brokkr-adapt → brokkr-sentinel` is governance→governance, which no invariant forbids, and §6.12 intends KVASIR to *consume* HEIMDALL's `screen` and the `Observation`/`Detector` surface. `cargo tree` confirms deps are `brokkr-core`, `brokkr-crypto`, `brokkr-sentinel` — **never `brokkr-reasoner`** (I-9), and no `brokkr-tools`/`brokkr-cli` (I-5).

**(b) What `generate` does — it gates, it does not invent.** The `DetectorDelta` cannot be derived from an incident id (§6.12). KVASIR holds the **authored** `(base, delta, generation)` (supplied by a human or external tooling, **never** the reasoner — there is no reasoner dependency). `generate` validates the seed (reading (c)), then stamps the pre-authored delta into a `RefinedDetector::new(...)`. Its only error is `UnconfirmedSeed`.

**(c) How a seed is confirmed — a seam, and the honest limitation is recorded.** P-6.1 requires a DAP-confirmed incident *recorded in Organ 5*; `brokkr-adapt` cannot depend on `brokkr-audit`. `generate` verifies the seed against a crate-local `ConfirmedIncidentLedger` seam — **not** the seed's own `confirmed_by` claim (a gate that trusts its input's own claim is not a gate). It refuses `UnconfirmedSeed` when the ledger has no confirmation, *or when the ledger's confirming DAP differs from the seed's* (a caller cannot pin a confirmation on a DAP who did not make it). **At Phase 9 the only ledger is a test double; the production binding — querying actual SAGA records — is the seam's Phase-11 implementation** (recording to Organ 5 is out of scope; querying it is Phase-11 wiring). The gate is structurally real *given a faithful ledger*; the ledger's fidelity to Organ 5 is the Phase-11 implementor's responsibility, not something committed types can verify. Recorded honestly in the conformance file.

- `tests/kvasir.rs` — 13 tests (real crypto).

**Design note (the seam pattern).** The core `MaturationPipeline` trait is minimal (spec + version + provenance + `now`); a `RefinedDetector` is a spec, not runnable. The rich context — authored delta, runnable candidate + incumbent detectors, labeled corpus, declared digest, seed class + sample, current versions, Self Set + HEIMDALL, DAP verify-key, ledger — lives on the concrete `Kvasir`, the same seam pattern SINDRI (key resolver) and HEIMDALL (Self Set corpus) use.

**The `SelectionPass.produced_at` decision (the R11 open question, now settled).** `select` has no `now` parameter and evaluates no expiry — KVASIR has **no** expiry gate, only version-equality and content checks. So `produced_at` is a held audit-trail stamp, not an evaluated clock; only `activate` takes `now` (§6.12, I-13). KVASIR holds no stored-clock field — the four-pattern held-clock grep is empty across all crate src.
