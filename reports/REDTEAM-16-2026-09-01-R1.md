## 1. Summary

**~28 attack vectors across black/white/grey at all noise levels; 14 runtime tests, all pass. 0 CRITICAL, 0 HIGH.** Seven findings, **F-32 … F-38** — two MEDIUM (a fail-open default and an unenforceable manifest granularity), five LOW/INFO (design observations). Every structural guarantee proven in Phases 13–15 is untouched; these findings are about the *new* AMD-011/Organ 5 wiring, and every one is a characterization of behaviour that ships today, asserted directly in a test.

| Category | Result |
|---|---|
| **A — black box** | The Capability Envelope, egress manifest, kill flag, trajectory, and provenance behave as their public API suggests, with two exceptions: capability governance is **fail-open by default** (F-33), and the egress manifest's port/protocol are **not enforced** (F-34). Trajectory sequencing is atomic and complete; provenance is present on every record and honest about its sensor |
| **B — white box** | `with_envelope` does **not** call `validate()` (F-32); the kill flag is a resettable `AtomicBool`, not a latch (F-36); egress host-matching is exact-string (F-35). Provenance is confirmed **inside the signed content** (a non-key-holder cannot rewrite how a record claims it was captured); records are Mutex-guarded and not externally mutable |
| **C — grey hat** | The envelope is self-declared, not attested against the environment (P-12.3 residual, F-32/C.1.1); the manifest is static by design; `permissive()` is a *valid* envelope but the enforcement gap is the missing `validate()` call and the fail-open default, not a malformed default |

**The thesis of this pass:** the AMD-011 surfaces are correctly *shaped* — the types validate, the gates are structurally present, the kill flag is unreachable by the model, the trajectory is complete and the provenance is signed — but the **orchestrator boundary is more permissive than the types allow**. It installs an envelope without validating it (F-32), defaults to non-enforcement (F-33), and enforces egress at host granularity while the manifest declares port+protocol (F-34). None of these is exploitable in BROKKR's *current* composition — it ships with a real `.with_envelope(..)` and no `Destination::Network` tool exists yet — but each is a gap between what AMD-011/P-12.4 specify and what the wiring enforces, and each would bite the moment the default is used or a network tool ships. **AMD-010 has no runtime surface to attack** (types only, dispositioned n.a.); it is documented in §4.

## 3. Findings (F-32 … F-38) — document, don't fix

| ID | Sev | Finding | Disposition |
|---|---|---|---|
| **F-32** | LOW-MED | **`Orchestrator::with_envelope()` does not call `CapabilityEnvelope::validate()`.** An orchestrator can be constructed and run with a `TierTooLow` or `TierMismatch` envelope; validation is the caller's documented responsibility. The drafted invariant I-14 ("validated before it governs") is not enforced at this boundary. The same family covers C.1.1 — the envelope is a *declaration*, not an *attestation* (P-12.3 residual). | **Gap for DAP.** A one-line `validate()` in `with_envelope` (returning `Result`, or debug-asserting) would close it; deferred per document-don't-fix. Not exploitable in the shipped composition, which supplies a valid envelope. |
| **F-33** | MEDIUM | **Capability governance is fail-open by default.** `new()` defaults `envelope = permissive()` and `egress_rules = None`, so an orchestrator built without `.with_envelope()` performs **no** egress enforcement and carries a permissive tier — in contrast to `guards = Guards::production()` (fail-safe default). A deployment that forgets `.with_envelope()` silently loses P-12.4. | **Gap for DAP.** Inconsistent safety posture vs the guards default. Options: default to a deny-all envelope, or require an envelope at `new()`. Deferred. |
| **F-34** | MEDIUM | **The egress manifest's port and protocol are structurally unenforceable.** `EgressRule` declares `{ destination, port, protocol }` per P-12.4 / ARCH §6.13, but `Destination::Network` carries only `{ host, channel }` — no port, no protocol — and `check_egress` matches host alone. A manifest intending "localhost:8443 HTTPS" actually admits "localhost, any port, any protocol." | **Gap for DAP.** Enforcement does not match the spec's stated granularity. Latent today (no `Destination::Network` tool exists), but would under-enforce the moment one ships. Closing it needs a port/protocol on `Destination::Network` and a full-tuple match. |
| **F-35** | LOW | **Egress host matching is exact-string.** `localhost` ≠ `127.0.0.1` (representation-sensitive, a false-deny risk), and `"*"` is a literal, not a wildcard. Combined with F-34, matching is simultaneously too strict (host spelling) and too loose (port/protocol). | **Design observation.** Exact-match is a defensible default (no accidental broadening); documented so the representation-sensitivity is known. |
| **F-36** | LOW | **The kill flag is not a latch.** A plain `AtomicBool` that any handle-holder can reset to `false` after setting it, resuming operations. "Once killed, stay killed" is not enforced. | **Design observation.** A latch (compare-and-never-clear, or a separate re-arm authority) would be safer for an independent-termination control. Deferred. |
| **F-37** | LOW | **The kill flag is a pre-hop check, not a mid-hop abort.** Checked once at the top of `run_hop`; a hop already inside tool execution runs to completion, and the flag stops the *next* hop. Termination latency is bounded by the longest single tool call, not immediate. | **By design** (ARCH §6.13: "checked before any gate on every call"). Named so the latency bound is explicit; a truly immediate abort would require cooperative cancellation inside tools. |
| **F-38** | LOW-INFO | **The trajectory is in-memory, not a SAGA event.** `TrajectoryEntry` lives only in `Mutex<Vec<..>>`; it has no `AuditEvent` variant and is volatile (lost on exit/crash). P-12.8 durable reconstruction rests on the individual SAGA event records (proposal/barrier/gate/signal), not the trajectory snapshot. | **Design observation.** Consistent with F-30 (SAGA durability ⇐ external persistence). If the trajectory is meant to be durable, it should be appended to SAGA or persisted alongside it. Deferred. |

**Severity note.** 0 CRITICAL, 0 HIGH. F-33 and F-34 are the two the DAP should weigh: both are gaps between AMD-011's specified behaviour and the orchestrator's enforcement, both are latent in the current composition, and both are cheap to close. The rest are honest design characterizations, several already acknowledged in the architecture (F-37 in §6.13, F-38 in the §13 in-memory-trajectory residual the Rev 1.18 draft adds).

## 4. AMD-010 — no runtime surface

`brokkr-core::explanation` is a **type surface only** (Option B): `ExplanationArtifact`, `ExplanationValidity`, `NullCause`, `TrainabilityReconciliation`, `CanaryAttestation`, and their kin, with no constructors beyond derive, no validation, no recording, and no orchestrator/SAGA/HEIMDALL integration. BROKKR runs a classical LLM, so OQGF-A-4 — and therefore OQGF-A-8…A-12 — is dispositioned `n.a.` (BROKKR-ARCH §1.4). **There is nothing to attack at runtime.** The one structural property worth noting held on inspection: `ExplanationValidity` has no variant in which a `Null` explanation is representable as `Valid` (OQGF-A-9), and its `Null` arm makes the OQGF-A-10 DAP acknowledgment an explicit `Option` a consumer must confront. No test is written against dead types; the disposition is recorded rather than exercised.
