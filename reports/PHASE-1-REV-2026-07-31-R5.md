## 3. `finding_id()` — determinism and injectivity (Task 4)

`finding_id()` is a **pure function of `(datum, condition)` only** — never `classification`, `reason`,
a counter, or a clock — because a DAP accepts a risk **before** the crossing is attempted (§6.5). It
lives in `brokkr-core` so the Barrier and any acceptance-issuing tool compute it identically.

**The encoding is injective.** It is `"<len>:<datum>:<condition-tag>"`, where `<len>` is the datum's
byte length. The length prefix — not a delimiter — bounds the datum, so a `DatumRef` that contains a
`:` cannot absorb the separator or the tag: a parser reads the decimal length to the first `:`, takes
exactly that many bytes as the datum, and the remainder (after the next `:`) is the tag. A bare
`datum:tag` concatenation would be ambiguous if the datum contained the separator; the length prefix
removes the ambiguity. `brokkr-core` has no hasher (it defines `Hasher` as a trait and implements
none), so this is injective string composition, not a digest. The condition tag is an **exhaustive**
match with no catch-all arm, so a new `BarrierCondition` variant forces a compile error. Injectivity,
determinism, and reason/classification-independence are each proven by a test (Task 7).

## 4. The doctest trap, handled and verified (Task 5)

Reshaping `BarrierFinding` made the I-2 `compile_fail,E0599` doctest's inline construction miss two
fields. Unfixed, it would have failed on **E0063 (missing field)** while `compile_fail` stayed green —
proving nothing about I-2, the same failure mode as the Rev 1.4 `Genome::new` arity trap. I updated the
construction to the four-field shape and **read the actual error code**: compiling the doctest body
standalone emits **`error[E0599]` and nothing else**. So the construction compiles and only
`.into_allow()` fails — the doctest proves I-2. The annotation stays `E0599` because that is what the
compiler emits.

## 5. The retype and the added variant (Task 6)

- **`RiskAcceptance::finding: RiskAcceptanceId → FindingId`** — a muddle corrected. The field means *a
  finding*, but `RiskAcceptanceId` is also what `BarrierVerdict::AcceptedRisk { entry }` carries (the
  acceptance entry's **own** id); one type served two referents, which is why the finding→acceptance
  link read as missing (no type meant *a finding*). The field doc records this; the module doc's
  historical note (`RiskAcceptanceId` predated `RiskAcceptance`) stays accurate and untouched.
- **`DeterministicGateId::Barrier`** — the enum held only `Genome`/`Mhc`, so an acceptance for an
  OQGF-I-10 barrier finding could not name its gate. `None` would misfile it as a **non-gate** risk
  (OQGF-P-10.4). The variant is documented with that reason.
