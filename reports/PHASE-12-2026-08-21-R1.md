## 0. Step-0 buildability determination

All infrastructure verified up before any code: ollama `llama3.2:3b` on `:11434`; nginx mTLS gateway on `:8443` (TLS 1.3, `ssl_verify_client on`, forwards to ollama); dev certs (PEM, EC P-384) at `~/BROKKR/certs/`. All required wolfSSL TLS symbols present in `libwolfssl.so.45` (`wolfSSL_CTX_new`, `wolfSSL_connect`, `wolfSSL_get_curve_name`, `wolfSSL_set_fd`, `wolfSSL_read/write`, `wolfSSL_CTX_load_verify_locations`, `wolfSSL_CTX_use_certificate_file`, `wolfSSL_CTX_use_PrivateKey_file`, `wolfTLSv1_3_client_method`, …).

**Four determinations that shaped the design (each a rule applied, not a preference):**

1. **The TLS FFI MUST live in `brokkr-crypto`, not `brokkr-bifrost` (the task's "Option A" is unavailable).** Two independent CLAUDE.md constraints force it: **§6** — `#![forbid(unsafe_code)]` in every crate except `brokkr-crypto`; and the **`links = "wolfssl"`** manifest key — only one crate may link a given native library, and that crate is `brokkr-crypto`. So Option A (FFI in bifrost) would require both relaxing §6 and a `links` collision. Option B (brokkr-crypto) is the only compliant location. The task delegated this to the builder; it resolves to B by direct application of the rules, not a gap.

2. **The committed `Bifrost` is pure clearance logic; the negotiated group is an *input*.** Its `evaluate_context(ctx, dest, now)` receives `dest` (with the group already on `Destination::Reasoner`) and delegates to HÚÐ. So the real handshake is a **producer** of the `NamedGroup` fact, not a change to the core `ContextClearance` trait. No core trait was touched.

3. **I-6 dictates where the model's network I/O lives.** I-6: *"There is no path from `brokkr-reasoner` to a network socket that does not pass through BIFRÖST."* So the socket to the model belongs to **BIFRÖST**, and MÍMIR's backend must reach the model *through* BIFRÖST. The transport therefore lives in `brokkr-bifrost` (`MtlsTransport`), and `brokkr-reasoner`'s `OllamaBackend` calls it — the path is `reasoner → bifrost → crypto → socket`, with no crypto/socket dependency added to the reasoner. (My first sketch put the TLS in the reasoner; re-reading I-6 corrected it.)

4. **No new external dependency.** MÍMIR uses **manual HTTP + manual JSON** over the BIFRÖST transport (the task's Option C). `serde_json`/`ureq` are not in the tree; adding one is a §6 supply-chain decision I did not make unilaterally.

## 1. What was built

### `brokkr-crypto/src/tls.rs` — the wolfSSL TLS 1.3 client (the second `unsafe` module)

- Raw `unsafe extern "C"` declarations for the TLS surface, matched to the wolfSSL 5.9.2 headers/symbols, in the same pattern as `ffi.rs`. Every `unsafe` block carries a `// SAFETY:` note; raw FFI types never escape.
- A safe `TlsClient` wrapper: `connect(&TlsConfig)` (TCP + mutual-TLS handshake, client cert presented, server verified against the CA), `negotiated_group() -> Option<String>` (via `wolfSSL_get_curve_name`), `write_all`, `read_until_close`. Owns the `WOLFSSL`/`WOLFSSL_CTX`/`TcpStream`; `Drop` frees the session then the context; the socket closes last. No panics, no indexing/slicing (uses `.get()`), fail-closed error codes.
- Confined exactly as `ffi.rs`: `lib.rs` does not `forbid(unsafe_code)` crate-wide (that would forbid the FFI); every *other* module still forbids it.

### `brokkr-bifrost/src/mtls.rs` — the real mTLS transport (the wire; I-6)

- `MtlsTransport::negotiate()` — handshakes, reads the negotiated group, returns `Negotiated { raw_name, group }`. Used to learn the channel fact **before** the clearance decision.
- `MtlsTransport::round_trip(request)` — **the model crossing**: opens a connection, writes the caller's HTTP bytes, reads the response. This is the one path from MÍMIR to the network (I-6).
- `map_group(raw_name) -> NamedGroup` — projects the raw wolfSSL group name onto core's closed `NamedGroup` vocabulary; PQC-hybrid groups map exactly, every classical curve maps to a classical variant (so `ChannelStrength::from_group` is correct).
- **No `unsafe` in this crate** — it calls the safe `TlsClient`. `brokkr-crypto` becomes a direct (was transitive) normal dependency.

### `brokkr-reasoner/src/ollama.rs` — the real model backend (through BIFRÖST)

- `OllamaBackend` implements the committed `ModelBackend` seam. `propose(payload, scope)` formats an ollama `/api/generate` POST (`stream:false`, `temperature:0`, a strict system prompt), sends it via `MtlsTransport::round_trip`, extracts the JSON `response` field, and parses an `Action`. It opens **no socket of its own** — no `brokkr-crypto` dependency in the reasoner.
- **Manual, dependency-free HTTP/JSON:** `json_escape` (request side), `json_string_field` (escape-aware extraction of a string field from the raw response), `parse_action` (strict `TOOL:`/`PATH:` lines, with a lenient fallback that recognizes the model's natural `write_file /path` phrasing). An unrecognized response yields an `unknown` tool the gate denies — **the model proposes; the spine disposes.**
- No `unsafe`; `#![forbid(unsafe_code)]` intact.

### `brokkr-cli` tests — live, `#[ignore]`

- `brokkr-crypto/tests/tls_smoke.rs` — a live mTLS handshake + a real `/api/tags` round-trip (proves the FFI).
- `brokkr-cli/tests/live_model.rs` — the full governed cycle with the real model (below).

## 4. Invariants

- **I-5** — dependency direction preserved. New edges: `brokkr-bifrost → brokkr-crypto` (direct; was transitive) and (unchanged) `brokkr-reasoner → brokkr-bifrost`. No governance crate depends on `brokkr-reasoner`/`brokkr-tools`/`brokkr-cli`; no cycle.
- **I-6** — the model's network I/O passes through BIFRÖST. `brokkr-reasoner` has **no** dependency on `brokkr-crypto` and opens no socket; its only route to the network is `MtlsTransport::round_trip`. BIFRÖST (the crossing) is the crate that does the model socket I/O — exactly what I-6 designates.
- **§6 unsafe discipline** — `unsafe` lives only in `brokkr-crypto`, now in two confined modules (`ffi.rs`, `tls.rs`), each with SAFETY notes.
- **I-12 / I-1 / I-13** — unchanged: `ClearedContext` still minted only by core's `clear`; `AuthorizedAction` only by SINDRI; `now` still per-call (the new modules hold no clock).

## 5. Honest limitations (named, not hidden)

- **The channel is classical.** nginx negotiated SECP256R1 (no PQC), so the effective authorization collapses to Public and the live test sends a Public context. PQC-hybrid needs a PQC-capable endpoint — a deployment concern, not Phase 12. Stated in the log and the record.
- **`NamedGroup` is a lossy projection for classical curves.** Core's closed vocabulary has no `Secp256r1`, so `SECP256R1` projects to the classical `Secp384r1` variant *for the channel-strength decision only* (both are Classical). The **raw name is preserved** (`Negotiated::raw_name`) and asserted/logged. Closing the label gap needs a core `NamedGroup` addition — out of scope.
- **Manual JSON assumes a contiguous `response` field.** True for a short, single-response ollama body; a multi-chunk body could split the field. A short coding proposal is single-chunk; noted.
- **The lenient parser hardcodes the one Phase-12 verb (`write_file`).** A general tool vocabulary in the parser is future work; the strict `TOOL:`/`PATH:` form is tool-agnostic.
- **TLS verifies the cert chain against the CA but does not enable hostname checking.** Sufficient for the dev CA; production should add domain-name verification. Named.
- **Dev cert paths, no AIBOM, no retry/pooling, no multi-hop conversation** — all per the task's §4 exclusions.

## 6. What this does not build

No PQC-hybrid TLS (gateway limitation); no AIBOM for the model (REGIN has no committed AIBOM surface); no production cert management; no retry/pooling; no multi-hop model conversation. `main.rs` unchanged.
