## 1. What I was doing

Beginning Phase 6: building HÚÐ, the Barrier. The phase's Step 0 requires reporting whether each of
Tasks 1–7 is buildable from the committed types **before writing a line**, and Task 6 (risk
acceptance) says explicitly:

> "If you cannot construct the finding->acceptance path without INVENTING an identity scheme (a hash
> of the reason string, a synthesized id, a convention about what `finding` means), **STOP and file a
> gap** — do not resolve it by picking the reading that compiles."

I checked. **Tasks 1, 2, 4, 5, and 7 are buildable; Task 3's Deny logic is buildable; Task 6 is
not.** Task 6 hits two committed-type shortfalls, either of which alone blocks it.

## 2. What the committed types do not resolve

### 2a. A `BarrierFinding` has no identity, and nothing links it to a `RiskAcceptance`

To return `BarrierVerdict::AcceptedRisk` **instead of** a `Deny` (§6.5: "the only sanctioned way past
is an AMD-006 `AcceptedRisk`"), the Barrier must decide **this finding is covered by that
acceptance**. The committed types give it nothing to decide with:

- `BarrierFinding` is `{ classification: Classification, reason: String }` (`barrier.rs:15-19`) —
  **no identity field.** Two distinct Denies with the same classification and reason are
  indistinguishable; a finding cannot be named.
- `RiskAcceptance.finding` is a `RiskAcceptanceId` (`risk.rs:42`) — an opaque `string_id!`
  identifier. `BarrierVerdict::AcceptedRisk { entry: RiskAcceptanceId }` (`barrier.rs:51`) carries the
  same.
- **There is no committed function or field linking a `BarrierFinding` to a `RiskAcceptanceId`**
  (verified by grep across `ids.rs`, `risk.rs`, `barrier.rs`). To match a would-be-Deny finding to an
  acceptance, I would have to **invent** the link: hash the `reason` string into an id, synthesize a
  `RiskAcceptanceId` from the finding's fields, or define a convention for what `RiskAcceptance.finding`
  means relative to a `BarrierFinding`. All three are the exact inventions Task 6 forbids.

**A resolver seam does not sidestep this.** The endpoint-ceiling and key resolvers match on a
**committed identity** (`ModelEndpointId`, `SubjectId`). A risk-acceptance resolver would have nothing
committed to match a `BarrierFinding` on — so defining its trait semantics would itself be inventing
the convention (`a convention about what finding means`), merely relocating the invention from the
gate body into a barrier-authored trait. The invention is still mine.

### 2b. `DeterministicGateId` cannot name the barrier gate

AMD-007 §AMD.5.1 makes the barrier's egress `Deny` a **Deterministic Gate** finding (OQGF-I-10
inheriting OQGF-P-2), whose only sanctioned way past is an AMD-006 acceptance. But:

- `RiskAcceptance.gate` is `Option<DeterministicGateId>` (`risk.rs:43`), and `DeterministicGateId` is
  `{ Genome, Mhc }` (`risk.rs:29-33`) — **no barrier variant.** The enum was built in the AMD-006 /
  `risk.rs` era, when AMD-006 §AMD.0.5 named only OQGF-G-4 and OQGF-M-1 as the Deterministic Gates.
  AMD-007 later made the barrier egress gate a **third** Deterministic Gate that also uses AMD-006
  acceptance, but `DeterministicGateId` was never extended.
- So a barrier-gate acceptance has **no correct `gate` value**: it is a gate finding (so `None` — "a
  non-gate risk, OQGF-P-10.4" per the field's own doc — is wrong), yet neither `Genome` nor `Mhc` is
  the barrier. The `RiskAcceptance` type **cannot correctly represent a barrier-gate acceptance.**

## 3. Why I cannot proceed without inventing something

To build Task 6 I would have to (a) invent an identity/matching scheme for `BarrierFinding` →
`RiskAcceptance`, and (b) either add a `DeterministicGateId::Barrier` variant myself (a `brokkr-core`
change, out of scope) or record barrier acceptances under a wrong `gate` value. Both are decisions
CLAUDE.md §1 reserves to the architecture and the DAP. Inventing a finding-identity scheme is
precisely the "builder authoring the governing vocabulary" hazard §4 forbids, and Task 6 names it.

## 4. What IS buildable (so the gap is precisely scoped)

Task 6 is the **sole** blocker. The Barrier's decide-Allow/Deny/Quarantine core is fully buildable:

|---|---|---|
| 1 — canonical BCR | Yes | all fields committed; domain tag `brokkr-barrier:bcr:v1` differs from `brokkr-genome:*` |
| 2 — BCR validation | Yes | `DualPublicKey::verify_dual` (both families), `now ≤ expiry`, `bcr.datum == flow.datum` |

| **6 — risk acceptance** | **No** | §2 |
| 7 — uncontrolled-channel register | Yes | barrier-local type, no core surface |

## 5. Why the whole phase stops (not "build 1–5, 7 and gap 6")

Step 0 directs a report **before writing** and a STOP if any task is not buildable, "rather than
discovering it after writing code." And §6.5 places the AMD-006 acceptance machinery **in this phase**
("built with the Barrier"), so a barrier omitting `AcceptedRisk` leaves an OQGF-P-9 obligation
**absent** — which §5.3 says stops the build regardless. Building the deny-only core now would also be
rework: a disposition that adds a finding-identity surface changes how the egress gate constructs
findings, and a `DeterministicGateId::Barrier` variant is a `risk.rs` change. So the phase stops cold,
as Phases 4 and 5 did, pending a core revision.

## 6. Recommendation (a recommendation only — I do not adopt it)

Placed by the DAP as a `brokkr-core` revision (never me), committed before Phase 6 builds under it
(§5.2). Additive options preferred:

- **(Preferred, additive) Give `BarrierFinding` a committed identity and add
  `DeterministicGateId::Barrier`.** e.g. a `BarrierFindingId` (or a typed condition/finding id on
  `BarrierFinding`), so a `RiskAcceptance` can reference a barrier finding by id and the gate can match
  a would-be-Deny to an acceptance by comparing ids — a real, non-invented check. Add
  `DeterministicGateId::Barrier` so `RiskAcceptance.gate` can name the OQGF-I-10 gate. This makes both
  §2a and §2b buildable and keeps acceptance in Phase 6 as §6.5 intends.
- **(Alternative) A committed acceptance-match key + resolver.** Commit, in core, a keyable identity on
  `BarrierFinding` (the §2a half), then a resolver seam matches on it. Still requires the finding
  identity; does not by itself fix §2b.
- **(Alternative) Defer the barrier `AcceptedRisk` path.** Declare that at Phase 6 the barrier's egress
  `Deny` is a hard fail with **no** acceptance path, deferring AMD-006 acceptance for the barrier gate
  until the finding-identity surface exists. The Barrier would build as a deny-only Deterministic Gate.

**Labeling per §4 (does any recommendation unblock me?):** the third option — "defer the `AcceptedRisk`
path" — **would unblock me**: it lets me build Tasks 1–5 and 7 immediately by simply never
constructing `AcceptedRisk`. I flag it. It is a *reduction* of what Phase 6 delivers (it omits an
OQGF-P-9 obligation §6.5 places here), and it is stricter (deny-only), so I am doubly wary of it; I
raise it only because it may be the DAP's intent (acceptance genuinely needs a core surface that does
not exist). My genuine preference is the first, additive option: it makes acceptance a real check and
resolves both shortfalls. I adopt none of them.

## 7. What is ready to build the moment this is disposed

Canonical BCR encoding (domain-separated from genome), BCR validation (non-circular, key supplied),
the nine-condition egress gate (Deny with a condition-naming finding), the ingress path
(Allow/Quarantine incl. the privileged-personal rule), the endpoint-ceiling resolver seam, and the
uncontrolled-channel register — all designed and determinable. Only the finding→acceptance link and
the barrier gate id await the core surface this gap asks the DAP to place.

## DISPOSITION — 31 July 2026 (annotation per §8; original body above is unchanged)

**Disposed by:** Jeremy Rose, DAP, via **Architecture Rev 1.8** (commit `e4d38a6`), §6.5 ("Risk
acceptance (AMD-006), and what a finding must carry"). The original body above is preserved verbatim.

**The DAP selected the additive option — give a barrier finding the identity an acceptance needs.**
Rev 1.8 places, and the `brokkr-core` Rev 1.8 revision (`reports/PHASE-1-REV-2026-07-31-R5.md`) builds,
exactly the surface this gap identified as missing:

- **§2a (no finding identity) — closed.** `BarrierFinding` gains `datum: DatumRef` (P-9.2's exact
  component identity) and `condition: BarrierCondition` (the precise advisory **as a value**, not
  prose). `BarrierFinding::finding_id()` derives a deterministic, pre-issuable `FindingId` from
  `(datum, condition)` only — so a DAP can scope an acceptance to a specific finding before the
  crossing. `RiskAcceptance::finding` is retyped `RiskAcceptanceId → FindingId`, correcting the muddle
  the gap named: `RiskAcceptanceId` also typed `AcceptedRisk { entry }` (the acceptance's own id), so
  no type meant *a finding*. `reason` remains, explanatory and **outside the match key**.
- **§2b (no barrier gate id) — closed.** `DeterministicGateId` gains a `Barrier` variant, so a
  barrier acceptance can name the OQGF-I-10 gate rather than being misfiled as a non-gate risk
  (`gate: None`, OQGF-P-10.4).

**The labeled self-interest disclosure was correct, and the labeled unblocking option was NOT
selected.** This gap's §6 flagged the third recommendation — "defer the barrier `AcceptedRisk` path" —
as one that **would unblock the builder** (build Tasks 1–5, 7 by never constructing `AcceptedRisk`) and
as a *reduction* omitting an OQGF-P-9 obligation §6.5 places in Phase 6. The DAP chose the **additive**
path — the harder one, which makes acceptance a real, matchable check — not the unblocking one. The §4
labeling rule worked as intended.

**§13 records that the promotion gate has the same defect, unfixed by design.** Rev 1.8 §13 (and the
§14 amendment note) record that `DeterministicGateId::Genome` has existed since Phase 1 — implying
acceptances for OQGF-G-4 promotion-gate findings are anticipated — but Phase 5 built no acceptance path
and `brokkr-genome`'s findings carry no identity either. **Rev 1.8 does not fix that**, because the
Barrier is what blocks Phase 6; reshaping the promotion gate's findings belongs with the phase that
revisits REGIN. It is named as a **scheduled correction rather than a later discovery.**

**The honoring rule is Phase 6, not this revision.** Matching a raised finding's `finding_id()`, a
`gate == Some(Barrier)` check, dual-family signature verification under a declared DAP key, and
`now <= expiry` (with reversion to blocking on expiry, OQGF-P-9.3) are the Barrier's, at Phase 6. This
disposition places the **type surface**; enforcement follows.

**Status:** DISPOSED — the finding-identity surface is committed (additive option). Phase 6 can now
express the finding→acceptance link it stopped on. No requirement relaxed.

— End of disposition, GAP-2026-07-30-001.
