## 1. What I was doing

Beginning Phase 5: building REGIN's OQGF-G-4 promotion gate, whose six predicates are stated in
BROKKR-ARCH §6.2 (Rev 1.4). I ground each predicate against the committed types before writing.
Predicates 1, 2, 3, 4, and 6 are cleanly determinable (§4 below). **Predicate 5 references an
"intent vocabulary" of recognized capabilities that the committed types do not provide**, and the
phase instruction directs me to stop rather than invent one:

> "Every declared tool's capabilities are declared: a ToolEntry naming a capability the intent
> vocabulary does not recognize fails. Read §6.2 and decide what 'recognize' means from the
> committed types; **if it is not determinable, STOP and report rather than inventing a vocabulary
> source.**"

The grounding instruction says the same at the phase level: "If §6.2 and the committed types
disagree anywhere, STOP and say so." They disagree here.

## 2. What the framework / committed types do not resolve

**§6.2 predicate 5** (BROKKR-ARCH line 431):

> | 5 | **Every declared tool's capabilities are declared** | a `ToolEntry` names a capability the
> intent vocabulary does not recognize |

For this to be a **fireable** check, there must be a committed set of "recognized" capabilities —
"the intent vocabulary" — that a tool's `required_capabilities` can be checked against and can fail.
There is none:

- `Capability` is an **open `String` newtype** — `brokkr-core/src/intent.rs:16`:
  `pub struct Capability(pub String);`. Every string is a valid `Capability`; the type "recognizes"
  everything. Under the literal reading ("the intent vocabulary" = the `Capability` type, §6.2
  line 316 "`Capability` is the intent vocabulary"), predicate 5 **can never fire**.
- **No register enumerates valid capabilities.** The six registers are `tools`, `cbom`, `aibom`,
  `endpoints`, `roots`, `policy` (`genome.rs`). None is a capability-vocabulary register.
- The **only** capability set derivable from the genome is the union of all
  `ToolEntry.required_capabilities` (the tool register). Checking a tool's capabilities against the
  set the tools themselves define is **vacuous** — every tool conforms by construction.

**Either way, predicate 5 as written is a predicate that can never fire.** And §6.2's *own*
predicate 6 (line 432, and the emphatic note at line 434) condemns exactly that:

> "a predicate that can never fire is a policy error, not a permissive default." … "An invariant
> that cannot fire is worse than absent: it reads as protection in the register while enforcing
> nothing."

So §6.2 cannot coherently intend predicate 5 to be the vacuous tool-union check (that would be the
very dead predicate it condemns), and the committed types provide no external "intent vocabulary"
to make it fireable. **§6.2 posits a vocabulary the committed types do not commit.**

## 3. Why I cannot proceed without inventing something

To implement predicate 5 I would have to supply "the intent vocabulary" from somewhere. Every
option is forbidden or wrong:

- **Invent a capability-vocabulary source** (a new register, an allow-list, "capabilities must be
  non-empty", "the vocabulary = policy's referenced capabilities") — inventing the authorization
  vocabulary Phase 5 exists to own, from a reading no committed type supports. §6.2 line 536 names
  this exact hazard ("the builder becoming the channel by which its own governing specification
  changes"), and the phase instruction forbids it in terms.
- **Implement it as the vacuous tool-union check** — a predicate that can never fire, which §6.2
  predicate 6 explicitly condemns. Shipping the dead predicate the architecture forbids is not
  conformance.
- **Silently omit predicate 5** and present a five-predicate gate as "the §6.2 OQGF-G-4 gate" —
  overclaiming completeness (§7), and `absent` under §5.3, which stops the build regardless.

All three are decisions CLAUDE.md §1 reserves to the architecture and the DAP. I decline to pick
the reading that compiles (the phase instruction's words).

## 4. What IS determinable (so the gap is surgical, and the rest is ready to build)

Predicate 5 is the **only** blocker. The other five predicates are fully computable from the
committed types, and the corpus requirement **OQGF-G-4 itself is satisfiable without predicate 5**
(it maps to predicates 1–3 plus M-6's predicate 4; predicates 5 and 6 are §6.2-added strictness):

| # | Predicate | Determinable? | Basis |
|---|---|---|---|
| 1 | All six registers present | Yes — **type-level** (I-10), not a runtime check | `Genome` has no `Option` register (`genome.rs`) |
| 2 | Every register signature verifies against the DAP root (explicit param) | Yes, **non-circular** | `DualPublicKey::verify_dual` over canonical bytes; root is a caller parameter, never read from the genome's own `RootsOfTrust` |
| 3 | No disallowed algorithm (`cbom.algorithms ∩ policy.disallowed = ∅`) | Yes | `AlgorithmId: PartialEq, Eq` (`genome.rs:69`) |
| 4 | No stale trust score (`now − reviewed ≤ 90 days`, saturating; future fails) | Yes | `Timestamp(pub u64)` (`ids.rs:46`); `now` an explicit param |
| **5** | **Tool capabilities recognized by "the intent vocabulary"** | **NO — this gap** | no committed capability vocabulary; see §2 |
| 6 | Every policy invariant well-formed (forbids a capability no tool declares, or forbids nothing) | Yes | reference set = union of `ToolEntry.required_capabilities`, a committed set; `forbids_*` emptiness is computable |

The asymmetry is itself the tell: **predicate 6 works because it checks *policy* capabilities
against a real committed set (the tool-union); predicate 5 fails because it checks *tool*
capabilities against a set that does not exist — the tools *are* the only capability set the
genome commits.**

## 5. Recommendation (a recommendation only — I do not adopt it)

The DAP to dispose predicate 5, placed as an architecture revision (never me). Options, additive
preferred:

- **(Preferred, additive) Commit a capability vocabulary.** Add a signed, DAP-owned source of
  recognized capabilities — most naturally a field on `PolicyRegister` (e.g.
  `recognized_capabilities: Vec<Capability>`) or a seventh register — against which predicate 5
  checks tool capabilities and predicate 6 checks invariant capabilities. This makes both
  predicates reference the *same committed vocabulary*, resolves the asymmetry, and makes predicate
  5 fireable (a tool naming a capability outside the declared vocabulary fails). A `brokkr-core`
  type revision, committed before Phase 5 builds under it (§5.2).
- **(Alternative) Redefine predicate 5 against a committed set already present.** If the DAP intends
  the tool-union to be the vocabulary, predicate 5 must be redefined to a *fireable* cross-register
  check (e.g. "every capability a policy invariant forbids is declared by some tool" — but that is
  predicate 6, so predicate 5 would need a different, stated target). The DAP states the target; I
  do not choose it.
- **(Alternative) Declare predicate 5 a type-level/structural guarantee like predicate 1** — i.e.
  not a runtime check — if the DAP judges tool capabilities are recognized by construction. This
  must be stated in §6.2, because a "runtime predicate that is actually vacuous" is the dead
  predicate §6.2 condemns; making it explicitly structural removes the contradiction.

**Labeling per §4 (does any recommendation unblock me?):** The third option — "declare predicate 5
structural / not a runtime check" — **would unblock me** without any new type, by removing a
predicate I cannot build. I flag it as such. It is a *reduction* of what the gate checks, so I am
doubly wary of it; I raise it only because it may be the DAP's actual intent, and the decision is
the DAP's. My genuine preference is the first (additive) option: it makes predicate 5 a real,
fireable check and resolves the predicate-5/6 asymmetry. I adopt none of them.

## 6. What is ready to build the moment this is disposed

So disposition-to-build is fast: canonical serialization (six domain-separated register encodings +
one genome encoding, following `brokkr-intent/src/canonical.rs` discipline), non-circular signature
verification (DAP root an explicit parameter), a `BarrierVerdict`-shaped two-state
`PromotionVerdict` (`Promoted` | `Blocked { findings }`, no downgrade path, typed findings), and
predicates 1–4 and 6 — all determinable and designed. Only predicate 5 awaits the vocabulary source
this gap asks the DAP to place (or the ruling that it is structural). The gate evaluates all
predicates and returns all findings; it is non-suppressible by construction (a `ToleranceGrant`
targets a `DetectorId`, which the gate does not have).
