checked each of `evaluate`'s five steps against them. Steps 1 (Signal 1) and 2 (Signal 2)

## 2. What the framework / committed types do not resolve

OQGF-M-11 requires **four** conjuncts for a grant: Signal 1 (identity, M-1), Signal 2 (a
valid Intent Provenance Chain, M-8), **the action lies within the current attenuated scope**,
and **the action respects the accumulated invariants** (M-10). The last two cannot be computed
from the committed types.

### 2a. Step 3 — action-in-scope (`AnergyReason::OutOfScope`) has no committed mapping

- `Action` is `{ tool: ToolId, detail: String }` — `brokkr-core/src/gate.rs:10-14`. It carries
  **no capability field** and no other structure identifying the authority it exercises.
- The scope is a set of `Capability(String)` — `brokkr-core/src/intent.rs:15-16, 27-29`;
  `IntentProvenanceChain::current_scope()` returns `&IntentScope`
  (`brokkr-core/src/intent.rs:168-173`).
- `ToolId` and `Capability` are **deliberately distinct** newtypes. `ToolId` is documented as
  the REGIN tool-genome identifier (`brokkr-core/src/ids.rs:28-29`); `Capability` lives in the
  intent vocabulary (`intent.rs:15`). **There is no committed function `Action -> Capability`,
  and no conversion between `ToolId` and `Capability`.**
- To check `current_scope().capabilities().contains(required_cap)` I must first know
  `required_cap`. Deriving it (e.g. `Capability::new(action.tool.as_str())`) is precisely the
  "silent convention" the instruction forbids: it would equate two types the design keeps
  separate and would **bind REGIN (Phase 5)** — whose job is exactly the tool→capability /
  tool→privilege vocabulary (BROKKR-ARCH §6.2: "the calling hop must hold the tool's
  privilege") — to a mapping invented by the gate. That inverts the roles the framework fixes:
  the builder would become the channel by which a later crate's governing vocabulary is set.

### 2b. Step 4 — action-respects-invariants (`AnergyReason::InvariantViolated`) has no committed semantics

- `Invariant` is `Invariant(String)` — `brokkr-core/src/intent.rs:56-57`;
  `current_invariants()` returns an accumulated `InvariantSet`
  (`brokkr-core/src/intent.rs:177-183`).
- Evaluating whether a given `Action { tool, detail }` **violates** an invariant such as
  `"no-network-egress"` or `"read-only-outside-src"` requires semantics that map an invariant
  string and an action to a boolean. **No such predicate exists in the committed types** — an
  `Invariant` is an opaque label, and an `Action`'s `detail` is an opaque `String`. Any
  implementation would be a policy engine invented here, binding future behavior.

## 3. Why I cannot proceed without inventing something

To write `evaluate`'s body I must decide what it does for steps 3 and 4. Every available
option is forbidden or unacceptable:

- **Invent a mapping** (tool-string = capability-string; parse invariant/detail strings) —
  forbidden by §4 and by the phase instruction; binds REGIN.
- **Silently skip steps 3–4** (return `Ok` on those dimensions) — a **fail-open** gate on two
  of M-11's four conjuncts: SINDRI would grant actions it has not checked for scope-fit or
  invariant-respect. That contradicts the prime directive and the gate's whole purpose.
- **Deny whenever scope/invariants can't be resolved** (fail-closed on 3–4) — makes SINDRI
  deny every action, since it can never resolve them. That is an unratified deny-all policy
  and would fail the M-11 positive test (a valid action must be `Granted`); it is also
  autoimmunity by construction (OQGF-P-1/P-5), the host-harm failure mode.

All three are decisions CLAUDE.md §1 reserves to the architecture and the DAP. This is the
"situation the framework does not cover" that §4 says to stop on.

## 4. Recommendation (a recommendation only — I do not adopt it)

The missing piece is a **committed action-semantics surface**: how an `Action` maps to the
`Capability` it requires, and how an action is tested against an `Invariant`. This is REGIN's
vocabulary (Phase 5) and/or a core type-surface addition. I recommend one of:

- **(Preferred) Add the action→capability binding to the type surface**, either as a
  `required: Capability` (or `Vec<Capability>`) field on `Action`, or as a REGIN-owned
  `fn required_capability(&Action) -> Capability` that SINDRI consumes through a trait it does
  not implement (the same seam pattern as `KeyResolver`). This keeps the tool→capability
  authority in REGIN while letting SINDRI perform the scope check against it. Placed by the
  DAP as an architecture/core revision, committed **before** Phase 4 builds under it (§5.2).
- **For invariants**, define a committed `InvariantEvaluator` seam (REGIN- or policy-owned)
  that returns violated/ok for `(&Action, &Invariant)`, so SINDRI evaluates invariants through
  an interface without owning the semantics. Until such a seam exists, the M-10
  action-evaluation clause cannot be enforced by SINDRI and stays **partial**.
- **Or**, if the DAP judges that SINDRI at Phase 4 should enforce **only** Signals 1–2 and that
  scope-fit / invariant-evaluation belong wholly to a later phase (REGIN wiring), then declare
  that explicitly as an architecture revision — reducing M-11's Phase-4 scope to the two
  cryptographic signals and deferring the two action-semantics conjuncts with a dated marker.
  That is a scope decision for the DAP, not a reading I may adopt.

**Labeling per §4 (does this recommendation unblock me?):** The third option — "SINDRI at
Phase 4 enforces only Signals 1–2" — **would unblock me**: it lets me build the crate
immediately without the missing mapping. I flag it as such. It is also a *narrowing* of what
SINDRI enforces, i.e. it makes the gate check *less*, so I would ordinarily be doubly wary of
recommending it; I raise it only because it may be the DAP's actual intent (Option B key
resolution already defers part of M-8), and the decision is the DAP's. The first two options
are *additive* (they add a committed surface so SINDRI can enforce *more*) and are my genuine
preference. I adopt none of them.
