## 1. What I was doing

Drafting a design to compute `VendorTrustScore::reconciliation_pass_rate` — OQGF-M-6's fifth factor, the one this architecture has carried as unmeasured since Rev 1.4.

The counter itself is easy and the precedent is exact: `HeimdallState` already holds `governed: u64` and `incidents: Vec<HostHarmIncident>` with `roll_window()` closing a window, so a pass/fail pair modelled on them is a small change. **The design is not blocked by the counter. It is blocked by what the counter would count.**

Three findings, one root cause.

## 2. Finding A — the fifth factor's input is degenerate, and computing it would fabricate a metric

`reconciliation_deviation` (`brokkr-sentinel/src/heimdall.rs`) classifies an `Observation::Hop`:

| Input | Result |
|---|---|
| `Hop { executed: Some(e) }`, `e != authorized` | `Some(detail)` — a deviation |
| `Hop { executed: Some(e) }`, `e == authorized` | `None` — a pass, and silent |
| `Hop { executed: None }` | `None` — authorized, never ran |
| non-`Hop` | `None` |

A pass is reachable as a *classification* inside `observe`, which holds the `Observation`. **That is not the problem.**

**The problem is the orchestrator's emission.** `brokkr-cli/src/lib.rs:897`:

```rust
authorized: action.clone(),
executed: Some(action.clone()),
```

**`executed` is a clone of `authorized`** — asserted, not derived from the execution. The orchestrator's own comment states the conclusion (*"the tool did exactly what was authorized"*) rather than observing it. `self.tool.execute()` returns `ToolOutcome { output: String }` (`brokkr-tools/src/tool.rs:20`), documented *"opaque to the governance spine — a tool's output is data, not authority"*, and it is never compared to anything.

**So `reconciliation_deviation` cannot fire from any production emission.** Every executed hop is a pass by construction. A counter over that input yields **exactly 1.0, always.**

### 2.1 Why a computed 100% is worse than the current `Score(0)`

`Score` is `pub struct Score(pub u8)` — *"a 0..=100 trust/score value (OQGF-M-6)"*, higher is better.

- **`Score(0)` today is inert.** Nothing computes the field and nothing reads it as a measurement, so it asserts nothing. It is a placeholder that happens to sit at the bottom of the range.
- **A computed `Score(100)` is an affirmative false claim.** It would be signed into the genome, dated, DAP-attributed, and read by the OQGF-G-4 promotion gate — and **indistinguishable at assessment from a genuine measurement.** An auditor requesting evidence for the fifth factor would be shown a number produced by comparing a value to a clone of itself.

**This is the R-6.2 defect class**: a declaration that overstates what deployment achieves, which AMD-018 §AMD.2.1 calls *"a conformance failure, not a documentation defect."* It is also §7's prohibition on fabricated completion, relocated from a report into a signed register — where it is harder to find and carries more authority.

**The brief anticipated a denominator including hops that could not have failed. The actual condition is the sharper one: the numerator contains only hops that could not have failed.**

## 3. Finding B — OQGF-M-12 is recorded SATISFIED on a tautology

Rev 1.19 moved OQGF-M-12 from `PARTIAL` to `SATISFIED`, on the ground that the live stream now exists — `executed: Some(..)` at `lib.rs:897` after a successful execution, `executed: None` at `:879` when an authorized action fails to run (14-FIX F-20).

**The stream exists. The comparison it carries cannot fail.** OQGF-M-12 requires that *"the action actually executed at each hop SHALL be reconciled against both the intent declared at that hop and the Root Intent."* What is reconciled today is the authorized action against a clone of the authorized action.

**The verdict must move to `PARTIAL`**, with the halves stated separately:

- **The mechanism is real and tested.** `Heimdall::observe` runs the comparison, a deviation raises a Signal through the graded-response path, and the A.6.1 statistical-reconciliation-failure trigger is wired. Fed a genuine deviation, it fires — the sentinel tests demonstrate this with supplied pairs.
- **The live input is vacuous.** No production emission can produce a deviation, so the mechanism has never had the opportunity to fire and cannot acquire one without a change outside `brokkr-sentinel`.

**This is the first verdict in this repository to move backward, and recording it as such is the point.** §5.3 permits it and warns that *"a conformance record whose verdicts only ever improve is not being audited."* Until now that sentence has been a principle with no instance; every verdict movement has been forward or a refusal to move. **A register that only ever improves is not being read**, and the first backward move is the evidence that this one is.

Rev 1.19 was not careless. It verified that the stream existed and that `executed: None` was correctly emitted — both true, both checkable, both checked. **What it did not check is whether the two sides of the comparison were independently derived**, which is the same shape as GAP-2026-09-10-001: a real question answered accurately, next to the question that determines the answer.

## 4. Finding C — OQGF-P-1's host-harm counters are never incremented in production

`record_governed_action` and `roll_window` are called **only** in `brokkr-sentinel/tests/sentinel.rs` at lines 534, 544, 551 and 561. **Neither appears anywhere in `brokkr-cli`.**

So in a running BROKKR the host-harm denominator stays at `0` and the window never rolls. `window_rate(0, 0)` returns `NaN` by design — *"a window that evaluated no governed actions has no evidence"* — so the reported rate is `NaN` forever, autoimmunity can never be detected, and the over-bound streak never advances.

**§13's characterisation is wrong and needs correcting.** It says:

> *"The host-harm rate is a lower bound, biased toward looking safe. Its numerator is confirmed host-harm incidents... so the measured rate under-states real host harm, and always in the same direction."*

That describes a rate that is measured and undercounts. **The rate is not measured at all.** The under-counting residual is real and remains true *of the design*; it is not true of the running system, where there is no numerator, no denominator, and no window. The correction belongs in Rev 1.31.

**Note what is not wrong.** The `NaN` discipline is exactly right and is why this is a recorded absence rather than a silent zero: `window_rate` refuses to return `0.0` from an empty window because *"a rate of 0.0 would claim safety from none."* The type is honest; the wiring is missing.

## 5. Root cause — a counter with no producer wiring, three times

| # | Counter | Producer | State |
|---|---|---|---|
| 1 | `reconciliation_pass_rate` | none — no accumulator anywhere | declared, encoded, `Score(0)` in every fixture |
| 2 | host-harm `governed` / `incidents` | `record_governed_action` / `roll_window`, **tests only** | `NaN` at runtime, forever |
| 3 | the pass/fail pair this design would have added | would have been `observe`, which *is* called | — |

**What follows for design, as an observation rather than a rule.** A counter that increments inside a method the orchestrator already calls is wired by construction; a counter behind a method the orchestrator must remember to call is wired by discipline, and #2 is what discipline produced. `Heimdall::observe` is called on every hop (`lib.rs:879`, `:895`); `record_governed_action` is called nowhere. **Had the reconciliation counter been placed, incrementing inside `observe` was the right site** — which is the one useful thing this Step 0 produces for whoever builds it later.

**This is not a proposed rule.** GAP-2026-09-10-001 recorded that inventing a rule per incident is how a framework acquires ceremony instead of control, and nothing here changes that. It is an observation about where counters belong, offered to the next design and not placed as a constraint.

## 6. Disposition — directed by the DAP at filing

1. **The M-12 reading of M-6's fifth factor stands.** The corpus phrase is *"statistical reconciliation pass rate"* — OQGF-M-3's vocabulary, and M-3 is `n.a.` for BROKKR. Taking the M-3 reading would make the factor `n.a.` and this work unnecessary, **which is reading a requirement down until it vanishes** — refused since Rev 1.2 and not reopened.
2. **The counter waits.** A computed tautology in a signed register is worse than an inert field.
3. **Whether `Score` can say "unmeasured" is placed in Rev 1.31**, proposed against what is committed rather than decided here.

**Labeled per §4, and the label is the load-bearing part of this report.** **Stopping is the outcome that saves me the most work.** The counter and window are genuinely easy — the `governed`/`incidents`/`roll_window` precedent is committed and I could have shipped a working pass-rate accumulator the same day, with tests that passed. The finding that makes it worthless is falsifiable in one line: read `brokkr-cli/src/lib.rs:897` and see whether `executed` is derived or cloned. **A reader who suspects I am avoiding work should check that line rather than accept this paragraph.**

## 7. What closing Finding A requires — scoped, not designed

**The executor must report what it did, distinguishably from what it was told to do.**

`ToolOutcome`'s opacity is not the defect — it is the correct posture for tool output as data, and §1.2's principle that a tool's output carries no authority depends on it. **It is, however, exactly why no reconcilable value exists**: an opaque `String` cannot be compared to an `Action`.

A genuine comparison needs an **effect description** the spine can compare against the authorized action: what the execution actually did, in the same vocabulary the authorization was expressed in. That touches:

- **`brokkr-core`** — a type the spine can compare against `Action`, in the governance vocabulary rather than tool-specific prose.
- **`brokkr-tools`** — every `Tool::execute` implementation must produce it, which is where the cost lives: an executor that cannot describe its own effect cannot be reconciled, and some will not be able to honestly.
- **`brokkr-cli`** — derive `executed` from that value rather than cloning `authorized`.

**Not designed here, deliberately.** The hard question is not the plumbing but what an effect description *is* for a tool whose effect is a file write versus a shell command versus a network call — and whether a tool that cannot describe its effect should be refusable at the genome rather than silently unreconcilable. That is a placement, and the builder does not place.
