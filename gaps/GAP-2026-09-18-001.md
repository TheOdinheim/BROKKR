## 1. What I was doing

Reporting the results of implementing `FactorEvidence` and promotion-gate predicate 8 (ARCH Rev 1.31 §6.2). In tracing which signed contents the change moved, I observed in passing that `VendorTrustScore::signature` *"has no signed-content function anywhere and is never verified."*

**That sentence was an aside in a report, which is exactly the class of claim this repository has been burned by** (GAP-2026-09-10-001: an assertion that was checkable, unchecked, and would have been relied on). It is verified here before being recorded.

## 2. Step-0 verification — the finding holds

Four checks at `82ef66a`, tree clean.

| # | Check | Result |
|---|---|---|
| 1 | A signed-content function for `VendorTrustScore` | **None.** `brokkr-genome/src/canonical.rs` exports exactly seven: `tools_`, `cbom_`, `aibom_`, `endpoints_`, `roots_`, `policy_`, and `genome_signed_content` (lines 459–514). There is no vendor-trust equivalent, so **there is nothing for the field to be a signature over.** |
| 2 | Anything that verifies it | **Nothing.** `grep` for `trust_score.signature` across the workspace returns no verification site — only the encoder that writes the bytes as data. |
| 3 | What predicate 2 verifies | **Six register signatures plus the genome's**, enumerated from `check_signatures`: `Register::{Tools, Cbom, Aibom, Endpoints, Policy, Roots}` and `GenomeSignatureInvalid`. **The trust score's is not among them.** |
| 4 | What fixtures put in it | **A placeholder.** `brokkr-genome/tests/promotion.rs:100` uses `dummy_sig()` — four zero bytes per family (`:36–42`); `brokkr-core/tests/negative_invariants.rs:530` uses `dual_sig()`. |

**The finding holds. It is also narrower than my aside implied, and the narrowing is the most useful thing in this report.**

## 3. What is *not* wrong — the accountability property is delivered, by a different mechanism

`write_vendor_trust_score` is called from `write_model_endpoint` (`canonical.rs:412`), which is called from `endpoints_signed_content` (`:480`). **So the entire trust score — all six factors, the new `evidence` pair, `reviewed`, `reviewer`, and the `signature` field's own bytes — is inside the endpoints register's signed content**, and predicate 2 *does* verify that signature against the DAP root.

Three consequences, and they matter for choosing a disposition:

- **The score is tamper-evident.** Its bytes cannot change without breaking the endpoints register signature and failing predicate 2.
- **The score is DAP-attributable.** `reviewer` and `reviewed` are covered by a signature made with the DAP key, so the attribution is attested — by the register, not by the field.
- **The `signature` field therefore adds no property that is not already provided.** It is not an unprotected value. It is a **redundant field shaped like an independent attestation**, where the attestation is actually supplied one level up.

**The code comment at `canonical.rs:400` is honest about this** and says so plainly: *"The trust score carries its own signature; the endpoint register commits to it as data (it is not one of the six register signatures the gate verifies separately)."* **The code is not lying. The type is what misleads**, and so is the architecture's §6.2 snippet, which shows `signature: DualSignature` on the struct with no qualification.

## 4. Why this is a defect rather than a harmless unused field

**A signature field is a claim that something was attested.** A reader of `VendorTrustScore` — or an assessor reading §6.2's type snippet, which is how an assessor would read it — concludes the vendor trust score carries its own attestation and is independently verifiable. **It does not and it is not.** Nothing computes it, nothing checks it, and there is no content defined for it to cover.

**This is the R-6.2 shape, inverted.** There, the architecture asserted a custody posture for eighteen revisions with **no field** behind it — a claim with nothing to check. Here there is **a field with no claim behind it**: the shape of an assurance, with no mechanism and no content. Both mislead a reader in the same direction, and the second is easier to miss precisely because a field *looks* like implementation.

**The severity is bounded and should not be inflated.** No security property is missing, because §3's mechanism supplies it. What is wrong is that the type over-states what is implemented, in a struct an assessor reads to evaluate OQGF-M-6. **A field that implies a second, independent attestation invites an assessor to credit BROKKR with one.**

## 5. Does any conformance verdict rest on this? No.

Stated plainly, because the question deserves a plain answer rather than a hedge.

**OQGF-M-6's text does not require the score to be signed.** Quoted: *"A vendor trust score SHALL be computed per supplier based on declared attestation capability, FIPS validation, breach history, jurisdictional exposure, and statistical reconciliation pass rate; the score SHALL be reviewed quarterly."* Five factors and a review cadence. **No attestation obligation on the score itself.**

**And the obligations M-6 does impose are checked by mechanisms that work:**

- *"reviewed quarterly"* — predicate 4 (`check_trust_score_staleness`), which refuses a score older than 90 days and one dated in the future.
- The five factors' presence — a type-level guarantee; `VendorTrustScore` has no `Option` factor.
- Attribution and tamper-evidence — the endpoints register signature, verified by predicate 2.

**So no conformance verdict currently rests on an attestation that is not checked.** OQGF-M-6 remains `PARTIAL` for the reason Rev 1.31 recorded — the fifth factor is unmeasured and unmeasurable from the current stream — and that verdict does not move in either direction on this finding. **I-10 is also unaffected**: it requires a *signed Endpoint Registry*, which is verified.

## 6. What closing it requires — scope, not design

Two dispositions, and the choice is the DAP's. **Neither is designed here and the builder does not place either.**

**(a) Give the field content and check it.** A `vendor_trust_signed_content` function, a signature computed over it, and a promotion-gate predicate verifying it against the DAP root. **What it would buy, stated honestly: very little.** The property is already delivered by the endpoints register signature, so this adds a second attestation of the same facts under the same key. It would be defensible if the intent were for a trust score to be signed by a *different* party than the register — a supplier-assessment role distinct from the genome owner — which is a governance decision, not a plumbing one.

**(b) Remove the field.** The honest expression of what exists: a trust score whose attribution comes from the register that carries it. **This has a cost worth naming:** it changes `write_vendor_trust_score` again, which moves `endpoints_signed_content` and `genome_signed_content` — **the third revision in three to move those bytes** (Rev 1.29's `PersonalDataTag`, Rev 1.31's `FactorEvidence`, and this). No persisted genome exists, so the cost is currently zero, and it will not always be.

**My reading, offered and not acted on:** (b) is more likely correct, because (a)'s value depends entirely on a governance intent — a separate signing party — that no document currently states. **But a field is not removed from a signed structure on a builder's reading**, and if the intent behind (a) exists somewhere in Odin's operating model, removing the field would destroy the hook for it. **The architecture would have to place whichever is chosen; this report asks, it does not answer.**

**Labelled per §4.** **Option (b) is less work for me than (a)** — a field removal and two fixture edits, against a new encoder, a signature computation, a predicate, and tests. I am recommending the cheaper one. The reason stands independently and is checkable: read `canonical.rs:412` and `:480` and confirm the register already covers the score. **A reader who suspects I am steering toward the easy option should verify that the property is genuinely already delivered, because that is the entire basis of the recommendation.**

## 7. The rule recommended at Rev 1.30 and still unplaced

Recorded here so it survives outside a chat message and can be placed or declined **deliberately rather than by forgetting**. Rev 1.30 §6.5 carries it, parenthetically, which is a poor place for something the DAP is meant to decide.

**The recommendation, verbatim from Rev 1.30 §6.5:**

> *"A recommendation, labelled per §4 because it would cost the builder work on every future revision rather than save any: if the DAP wants a rule, the narrow one worth considering is that **a revision asserting a consequence about committed code names the file and symbol it checked**, which is what the §5.4 table already does for inputs. Recommended, not placed."*

**The reasoning for it.** §5.4 requires a placed *rule* to name the path to the values it reads. It says nothing about a revision's claims about *consequences* — what a type change will and will not touch. GAP-2026-09-10-001 is exactly that gap: Rev 1.29 asserted the `PersonalDataTag` change did not reach the audit chain, the claim was checkable in two greps, it was not checked, and it would have been relied on by whoever assessed the next encoding change. A rule requiring a consequence-claim to name its evidence would have caught it, because the drafter would have had to write down *which* encoder they looked at — and writing "brokkr-barrier's `write_personal`" would have raised the question of whether another crate had one.

**And the reasoning against, which the DAP should weigh equally.** The counter-argument is recorded in the architecture in the same breath as the recommendation, and it is not weaker: *"Adding a rule per incident is how a framework acquires ceremony rather than control."* Every gap so far has been caught by the practice that is already mandatory — a builder grounding a placed design against the tree at Step 0, which found this one, GAP-2026-09-07-001, GAP-2026-09-08-001, GAP-2026-09-10-001, and GAP-2026-09-15-001. **A rule that duplicates a working practice adds a box to tick and does not add a check.** CLAUDE.md §12.1 makes the same argument about invariants: one that enforces the presence of a claim while the claim's truth lives elsewhere *"teaches a reader that the invariant set covers something it does not."*

**The honest position between them:** §5.4 exists because *naming the pattern did not prevent repeating it* — awareness was maximal and insufficient (CLAUDE.md §5.4's own closing argument). That argument applies to consequence-claims as much as to inputs. Whether it applies *enough* to justify a fifth checked rule is a judgment about how much process this repository can carry before the process becomes the work, and **that is a DAP judgment, not a builder's.**

**Recording is not placing.** This report does not adopt the rule, and the builder may not. It remains **unplaced**. If the DAP declines it, that decision should be recorded too, so a future reader sees a considered refusal rather than an idea that evaporated.

**Labelled per §4.** **This item increases my work in both directions and is recorded against my own interest.** If placed, it costs me a named-evidence check on every future revision I draft. If declined, the decision closes an avenue I raised. Neither outcome benefits me, which is the only reason worth trusting in a recommendation a builder makes about the rules that bind it.
