## 1. What I was doing

The AMD-008 / AMD-009 delta check: enumerating OQGF-P-10.1…P-10.6 and OQGF-P-11.1…P-11.7
from the amendment text and asking, for each, whether it imposes a type-level obligation
on `brokkr-core` that the crate as built is missing.

## 2. What `brokkr-core` is missing (bucket B)

`brokkr-core` was built and conformance-checked against **eight** amendments. Two new
requirements impose **core type obligations that are absent**:

**From OQGF-P-10 (Risk Register), a core type surface that does not exist:**

| Requirement (text) | Missing core type | Required shape |
|---|---|---|
| P-10.1 "SHALL maintain a Risk Register recording … description … likelihood … impact … a named DAP owner … exactly one disposition" | `RiskRegister` trait; `RiskEntry` struct | `RiskEntry { id: RiskId, description, context, likelihood: Likelihood, impact: Impact, owner: Dap, source: RiskSource, disposition: Disposition }`; `RiskRegister` with `record`/`inventory` |
| P-10.3 "exactly one disposition from the set {Avoid, Reduce, Transfer, Accept}" | `Disposition` enum; `TreatmentPlan` | `enum Disposition { Avoid{plan}, Reduce{plan, residual}, Transfer{mechanism, residual}, Accept{acceptance} }`; `TreatmentPlan { owner: Dap, target: Timestamp, status: TreatmentStatus }` |
| P-10.5 "tracked to completion … remain visible … as an open item … Residual Risk SHALL be re-assessed" | `TreatmentStatus`; `residual` field | `enum TreatmentStatus { Open, Executed }`; `residual: RiskEntry` on Reduce/Transfer |
| P-10.4 "An Accept disposition SHALL carry the accountability properties of an OQGF-P-9 Risk-Acceptance Entry" | `RiskAcceptance` struct (AMD-006 shape) | `RiskAcceptance { finding, gate, dap: Dap, justification, expiry: Timestamp, signature: DualSignature }` — core has only `RiskAcceptanceId` today |

**From OQGF-P-11 (Personal Data), a classification dimension that does not exist:**

| Requirement (text) | Missing core type | Required shape |
|---|---|---|
| P-11.1 "mark it with a Personal-Data Tag: a Data Classification dimension … orthogonal to … the sensitivity tier … regardless of the datum's sensitivity tier, including where that tier is Public" | a personal-data dimension in `classification.rs` | a marker/field composing orthogonally with `Classification` (e.g., a `PersonalData` marker carried alongside the tier) — **never** a new `Classification` variant, which would conflate the orthogonal dimensions |

Everything else in the two amendments (P-10.2, P-10.6, P-11.2–P-11.7) is behavioral or
lands in `brokkr-crypto` (Phase 2, crypto-shredding), `brokkr-genome` (Phase 5, AIBOM
minimization), `brokkr-barrier` (Phase 6, BCR purpose/retention, minimization gating), or
`brokkr-audit` (Phase 7, register persistence, erasure tombstone, subject-rights query,
personal data in the accountability record). Those are out of scope for `brokkr-core` and
are recorded in the delta so they are checked at their phases, not dropped.

## 3. The one design decision the DAP must make (P-10.4 dependency)

A **core** `Disposition::Accept` cannot hold a **Phase-6 barrier** type, because
`brokkr-core` may not depend on `brokkr-barrier` (I-5). AMD-006 §5.1 places
`RiskAcceptance` in `oqgf-core`; Phase 1 (per its scoped list) built only
`RiskAcceptanceId`. AMD-008 forces the resolution: **the `RiskAcceptance` struct must
enter `brokkr-core`** so `Disposition::Accept` can carry it. This is not a new mechanism —
it is the AMD-006 accountability shape, placed where AMD-006 already said it belongs.

## 4. Why I cannot proceed without a decision

Building these types is a Phase-1 revision, and CLAUDE.md §1 reserves scope to the
architecture and the DAP: I do not decide what `brokkr-core` should contain. Two points in
particular are the DAP's to settle, not mine:

- **The `RiskAcceptance` placement** (§3) — confirm it moves into `brokkr-core`.
- **The personal-data dimension's exact core surface** (P-11.1) — whether it is a marker
  type in `classification.rs`, a field on a composed classification, or another shape. I
  have flagged that a personal dimension composing with the core `Classification` is most
  faithfully a core type; the precise form is an architecture decision.

Per CLAUDE.md §4, the architecture document is where such shapes are placed, and the DAP
places revisions of it — the builder never does.

## 5. Recommendation (and the §4 unblock check)

**Recommendation:** open a **Phase 1 revision (R3)** scoped to exactly the types in §2 —
the Risk Register surface (including `RiskAcceptance` into core) and the personal-data
classification dimension — with negative/positive tests, and no behavior and no other
crate. This ADDS types and relaxes nothing.

**§4 unblock check:** this recommendation is the *harder* path. The disposition that would
have unblocked me — declaring every requirement C so "Phase 1 stands, no revision" — was
available and I declined it. Flagging B as non-empty creates work; it does not clear a
blocker. So the recommendation and my convenience point in **opposite** directions, and
there is no self-serving coincidence to disclose beyond noting that fact.
