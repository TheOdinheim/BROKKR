## 2. The defect — the design places rules against fields the API does not expose

Rev 1.24 §6.9 places three rules that read fields of an RFC 3161 token:

| Rev 1.24 rule | Value it must read | Where that value lives |
|---|---|---|
| *"its `messageImprint` equals the digest of the bytes BROKKR actually sent"* | `messageImprint` | inside `TSTInfo` |
| record `gen_time` — *"the `genTime` the authority asserted"* | `genTime` | inside `TSTInfo` |
| record `algorithm` — *"the TSA's signature algorithm"* | signature algorithm OID | `SignerInfo` / `pkcs7->publicKeyOID` |

**`wolfSSL implements CMS, not RFC 3161.`** `wc_PKCS7_VerifySignedData` verifies the CMS `SignedData` signature and returns a status code — **that half works and needs no struct access.** But `TSTInfo` is the CMS **eContent**, and the only route to it is the struct field `pkcs7->content` (`wolfssl/wolfcrypt/pkcs7.h:247`, `byte* content; /* inner content, not owner */`).

**All 54 exported `wc_PKCS7_*` symbols were enumerated.** There are six getters:

| Exported getter | Returns |
|---|---|
| `wc_PKCS7_GetAttributeValue` | a **signed attribute** by OID — not the eContent |
| `wc_PKCS7_GetEnvelopedDataKariRid` | an enveloped-data recipient identifier |
| `wc_PKCS7_GetNoCerts` | a flag |
| `wc_PKCS7_GetPadSize` | an arithmetic helper |
| `wc_PKCS7_GetSignerSID` | the signer identifier |
| `wc_PKCS7_GetStreamMode` | a flag |

**None returns `content`, `contentSz`, or `publicKeyOID`.** The one remaining name matching "content" is `wc_PKCS7_SetContentType`, a setter for the content-type OID, not a getter for content bytes.

### 2.1 What this costs, precisely

- **`TimestampError::ImprintMismatch` cannot be implemented.** Rev 1.24 §6.9 names it *"the one variant here that is an attack signature"* — a token attesting bytes BROKKR did not send is a substituted response or a TSA stamping something else. It is the single most important failure the design defines, and the placed route cannot reach the field it turns on.
- **`gen_time` cannot be recorded.** Same field, same reason.
- **`algorithm` has only a partial workaround.** It could be derived from the TSA certificate's public-key type via `wc_ParseCert`/`wc_InitDecodedCert`, which **are** exported and were already in the build. But that is an **inference from the certificate, not an observation of the token's `SignerInfo`** — and Rev 1.24's whole treatment of the PQC clause turns on recording what the token actually says. Labelling an inference as an observation is the same honesty failure the revision exists to prevent, one size smaller.

## 3. Root cause — existence checked, reachability not

**This is the finding, and it is more useful than the blocker.**

Rev 1.24 §6.9 recorded a verification, dated and specific, and it was true:

> *"**wolfCrypt has PKCS#7/CMS natively and it is not enabled in the current build.** `wolfcrypt/src/pkcs7.c` is present, `wc_PKCS7_VerifySignedData` is in it, and `--enable-pkcs7` exists with **default: disabled**; `nm -D` on the linked `libwolfssl.so.45.0.0` reports **zero** PKCS7 symbols."*

Every clause of that is accurate, and **none of it is the check that mattered.** It established that the library *has* CMS. It did not establish that **the evaluating code has a path to the values the design's rules read** — `messageImprint` and `genTime`. The rules were placed against fields whose reachability was never tested.

**That is CLAUDE.md §5.4, exactly, one level down.** §5.4 requires that *"for any predicate, gate, or rule placed against a value, verify that the evaluating code has a path to an instance of that value — not merely that the value's type is defined."* Rev 1.21 placed a predicate against a **tier** the gate could not reach. Rev 1.24 places a rule against a **field** the API does not expose. Same rule, same failure, different noun.

### 3.1 The fifth instance, and the first committed after the rule meant to prevent it

GAP-2026-09-07-001 §4.1 tabulated four. This is the fifth, and its position in the sequence is the part worth recording:

| Revision | Placed a rule against | Gap | Relative to §5.4 |
|---|---|---|---|
| Rev 1.4 | a capability vocabulary that did not exist | GAP-2026-07-27-001 | before |
| Rev 1.6 | personal data the flow could not see | disposed by Rev 1.7 | before |
| Rev 1.7 | a barrier finding with no identity | GAP-2026-07-30-001 | before |
| Rev 1.21 | a conformance tier the gate could not reach | GAP-2026-09-07-001 | **the instance that produced §5.4** |
| **Rev 1.24** | **token fields the PKCS#7 API does not expose** | **this report** | **after §5.4 was placed** |

**§5.4 was written in response to the fourth instance, placed by the DAP at Rev 1.22 and CLAUDE.md v1.10, and the very next architecture draft did not apply it.** Rev 1.24 §6.9 carries a §5.4 table — it lists seven rules and their paths, and correctly records one rule as deliberately unplaced. **The table covers the rules that read values held by BROKKR** (the imprint bytes, the trust anchor, the current time) **and does not cover the rules that read values held inside the token.** The check was performed on the half where the answer was already known and skipped on the half where it was not.

GAP-2026-09-07-001 §4.1 concluded that *"naming the pattern did not prevent repeating it"* and argued from that for a checked rule rather than a reminder. **This instance is the stronger version of that argument: the rule existed, was placed, was cited in the very document that violated it, and still did not prevent the fifth occurrence.** A rule a drafter can satisfy partially — by tabulating the easy rows — is a rule that can be passed without being applied. That is worth the DAP's attention more than the blocker is.

**I drafted Rev 1.24, and I proposed §5.4.** Both facts belong in this report, because the DAP relied on a §5.4 table I wrote in a document I wrote, and the table was incomplete in exactly the direction that would have stopped the draft.

## 4. Buildability determination (so the gap is precisely scoped)

| Item | Buildable | Basis |
|---|---|---|
| HTTP transport for the timestamp query | **Yes** | Hand-rolled `POST`, the `brokkr-reasoner/src/ollama.rs` precedent; a single request/response, simpler than the committed one |
| CMS signature verification against a trust anchor | **Yes** | `wc_PKCS7_Init` / `wc_PKCS7_InitWithCert` / `wc_PKCS7_VerifySignedData` / `wc_PKCS7_Free`, all exported; a status code, no struct read |
| TSA certificate handling | **Yes** | `wc_ParseCert`, `wc_InitDecodedCert`, exported and already in the build before the rebuild |
| `TimestampError::{Unreachable, Malformed, SignatureInvalid}` | **Yes** | All three are decidable from transport status and the verify return code |
| **`messageImprint` comparison → `ImprintMismatch`** | **No** | No path to the eContent (§2) |
| **`gen_time`** | **No** | Same |
| **`algorithm` as an observation** | **No** | `publicKeyOID` unreachable; only a certificate-derived inference is available (§2.1) |

**Why nothing was written, not even the buildable majority.** Shipping the transport and CMS verification while `ImprintMismatch` cannot fire would produce a client that obtains tokens, verifies their signatures, and **cannot tell whether the token attests the record it was requested for.** A token that verifies but attests other bytes would be stored as `Timestamping::Token` — a valid-looking third-party attestation of something else, in a signed audit record. That is worse than the current `Unavailable`, which at least tells the truth. The same reasoning GAP-2026-08-19-001 §5 used to stop a whole phase rather than ship four of six tasks applies here with a sharper edge: the missing piece is the one that detects substitution.

## 5. Refused routes, and why the reasoning is the point

Four routes reach the fields. Each is recorded with its objection, because the objections are the substance of the disposition.

- **Offset-read the `wc_PKCS7` struct from Rust.** `brokkr-crypto/src/ffi.rs` never reads C struct fields — it passes **opaque pointers** and uses probed *sizes* for stack buffers, never offsets. And the layout is configuration-dependent: `pkcs7.h` guards `streamOutCb` and `streamCtx` behind `#ifdef` **before** the fields needed, so an offset correct for one build is silently wrong for another. **A silently wrong offset does not crash; it yields a wrong `messageImprint` comparison or a wrong recorded algorithm — a false statement in a signed audit record**, which is the precise failure the whole A-3 design exists to prevent.
- **Hand-walk the token's DER to locate the eContent.** This parses **unauthenticated, attacker-supplied bytes** — the eContent's position must be found *before* anything about the token has been verified. Rev 1.24 §6.9 rejects exactly this: *"exactly the class of code where CVEs live, and not something to hand-write for a security boundary."* (wolfCrypt's exported `GetASNTag`/`GetLength` primitives would supply the bounds checking, but they cannot help: they parse *from* a position, and obtaining the position is the unauthenticated walk.)
- **Reduce the token record to what is reachable.** Drop `gen_time` and `ImprintMismatch`, record a certificate-derived algorithm. **This guts the design's central attack case** and would let a substituted token be stored as a valid attestation. It is also the route that unblocks fastest and costs least (§6, labelled).
- **Add a Rust DER/CMS dependency (`der`, `cms`, `x509-cert`).** A §6 supply-chain decision, and one with a specific objection beyond cost: it puts **a parser outside our control into the audit path** — structurally the same exposure as hand-walking DER, with a better-reviewed implementation and a nicer wrapper. It also discards Rev 1.24's own reason for choosing wolfCrypt, which was to avoid raising a supply-chain decision at all.

## 6. Disposition — directed by the DAP at filing: the C shim

Recorded as a directed disposition, not a builder recommendation. **It requires Architecture Rev 1.25 before implementation resumes** (§7).

**A small C translation unit exposing accessors for `content`, `contentSz`, and `publicKeyOID`, compiled with the same flags as the library.**

**Compiling it with the library's own flags is the whole of why it works**, and it is worth stating rather than assuming: the `#ifdef` layout problem in the refused offset-reading route arises because *Rust* would be guessing at a layout determined by C preprocessor state. A shim compiled against the same headers with the same flags **sees the same struct layout wolfSSL itself sees** — it is not guessing, it is being told by the compiler. The fragility is not reduced; it is eliminated, because there is no second party forming an independent opinion about the layout.

It is a build-system change, it is small, and it is auditable — a handful of field reads with no logic. It keeps the FFI boundary where it already is rather than opening a new one.

**§4 labelling — does the disposition unblock me?** Yes, and so does every route in §5; the unblock is intrinsic, since the values must come from somewhere. What matters for the DAP's weighing is the ordering: **the route that unblocks me fastest and costs me least is the one I did not recommend** — reducing the token record — and it is the one that removes the attack case. The C shim and the Rust dependency both create more work than that; the shim creates the most, since it adds a build-system surface this repository has never had. I adopt none; the DAP has ruled.

## 7. Closure path

1. **Architecture Rev 1.25** (DAP-placed) places the shim: what it exposes, where it lives, how it is compiled, what it does **not** do, and — since exposing the eContent does not parse it — **where the `TSTInfo` parse happens and under what constraints**, stated plainly rather than routed around.
2. **Commit 1 (`brokkr-crypto`)** then places the shim, its build integration, and the FFI bindings, inside the one crate permitted `unsafe`.
3. **Commit 2 (`brokkr-audit` + `brokkr-cli`)** then places the client, the two new `TimestampError` variants, `TimestampSigAlg`, and the wiring, with a hermetic `openssl ts` test responder.
4. **Expected consequence, unchanged:** **A-3 remains PARTIAL after the client ships**, on the **PQC clause** rather than the mechanism — no publicly operated RFC 3161 authority signs post-quantum. A self-hosted responder satisfies the mechanism and fails the Organ 5 independence principle, and is a test path only.

**No requirement is relaxed by this report.** It records that a placed design cannot be implemented as placed, and asks for the surface that makes it implementable. **OQGF-A-3 remains PARTIAL**, and nothing here is progress toward the PQC clause, which no code in this repository can close.
