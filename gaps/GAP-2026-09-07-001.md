## 1. What I was doing

Implementing the design Architecture Rev 1.21 (commit `2c97d15`) placed for the CBOM key-custody
declaration — the third of R-6.2's three elements, and the only one that is code (Rev 1.21 §6.11,
GAP-2026-09-06-001 §8). Two commits were specified per CLAUDE.md §5.2: the `brokkr-core` types
first, then the consuming promotion-gate predicate.

Step 0 grounds each commit against the committed types before any edit. **Neither commit is fully
buildable as placed.** One blocker is fatal to Commit 2; the other is a small but genuine design
choice in Commit 1.

## 2. Blocker 1 — predicate 7 checks a tier the gate cannot reach

Rev 1.21 §6.2 places predicate 7 as a **tier-consistency** check, deliberately rather than as a
presence check (the presence form can never fire, which that section explains at length):

| # | Predicate | Fails when |
|---|---|---|
| 7 | **The declared key custody satisfies the genome's declared conformance tier** | `cbom.custody` does not meet the AMD-018 tier obligation for **`genome.tier`** … |

**There is no `genome.tier`, and nothing the promotion gate can read supplies one.**

| Where a tier could have come from | State |
|---|---|
| `Genome` (`brokkr-core/src/genome.rs:270–281`) | `version, tools, cbom, aibom, endpoints, roots, policy, corpus_digest, owner, signature`. **No tier.** |
| `Cbom` (`genome.rs:79–87`) | `cyclonedx, algorithms, signature`. No tier (and no custody field either — that is what Commit 1 adds). |
| `PolicyRegister` (`genome.rs:222–233`) | `capabilities, invariants, disallowed, signature`. No tier. |
| `promote(...)` (`brokkr-genome/src/gate.rs:30`) | `(genome: &Genome, dap_key: &DualPublicKey, now: Timestamp)`. No tier parameter. |
| `ConformanceTier` (`brokkr-core/src/capability.rs:26`) | **Exists** — `{ Baseline, Enhanced, HighAssurance }` — but only as a field of AMD-011's `CapabilityEnvelope`, which lives on the orchestrator in `brokkr-cli`. `brokkr-genome` reaching it would invert I-5. |
| Anywhere in genome-reachable code | No declared conformance tier exists. §1.4 declares Enhanced **in prose**. |

The predicate as placed cannot be implemented. There is no reading of it that is buildable without
inventing a tier source, and inventing one is choosing a governance-relevant location for a signed
fact — CLAUDE.md §4 forbids it, and the instruction forbade adapting the placed design.

## 4. Root cause — existence is not reachability

**This is the finding, and it is more useful than either blocker.**

Rev 1.21 carried a verification note, written by me, listing what had been checked against source
before drafting. It included:

> *"`ConformanceTier { Baseline, Enhanced, HighAssurance }` already exists in
> `brokkr-core::capability`, so predicate 7 needs no new tier vocabulary."*

**The sentence is true. It is not the check that mattered.** I verified that the *type* was defined
and never verified that the *evaluating code had a path to an instance of it*. Those are different
questions, and only the second one determines whether a predicate can be written. The DAP relied on
that verification note as covering predicate 7's buildability, and it did not cover it — it covered
a neighbouring fact that reads like it.

The same error, in miniature, produced Blocker 2: `Digest` and `Timestamp` were verified to exist,
and `KeyRef` was written into the design without the same check being applied to it at all.

### 4.1 This is the fourth instance, and it was committed in the document that lists the other three

Rev 1.21's own change log enumerates the pattern:

> *"Rev 1.4's predicate 5 against a vocabulary that did not exist, Rev 1.6's egress rule against
> personal data it could not see, and Rev 1.7's acceptance machinery against a finding that could
> not be named."*

To which this gap adds: **Rev 1.21's predicate 7 against a tier it cannot read.**

| Revision | Placed a rule against | Gap |
|---|---|---|
| Rev 1.4 | a capability vocabulary that did not exist | GAP-2026-07-27-001 |
| Rev 1.6 | personal data the flow could not see | disposed by Rev 1.7 |
| Rev 1.7 | a barrier finding with no identity | GAP-2026-07-30-001 |
| **Rev 1.21** | **a conformance tier the gate cannot reach** | **this report** |

Three of the four were caught at Step 0 by the builder before code was written, which is the control
working. What is new here is that **the fourth was written into the very document that enumerated the
first three**, by the party that enumerated them, in a revision whose verification note asserted the
relevant check had been performed. Naming the pattern did not prevent repeating it. That is worth
recording precisely because it disconfirms the cheapest available remedy — awareness.

## 5. Proposed Step-0 rule (proposed, not adopted)

A rule that would have caught both blockers, and all three prior instances:

> **For any predicate, gate, or rule placed against a value, verify that the evaluating code has a
> path to an instance of that value — not merely that the value's type is defined.** Record the path
> (the field, parameter, or seam through which the evaluator obtains it), or record that none exists.
> A type that is defined but unreachable from the evaluator is, for the purpose of a placed rule,
> absent.

It generalizes the check §5.3 already requires of conformance verdicts — *"the file, type, and
function that satisfies it — **or that none does**"* — from requirements to placed rules, and it
would have failed Rev 1.21 at drafting: `ConformanceTier` is defined, and no field, parameter, or
seam carries one into `promote`.

**Labeling per CLAUDE.md §4 — does this proposal unblock me?** No, and it is the opposite. **This
rule is the builder's own obligation and adopting it costs the builder work** on every future
placement: an extra reachability trace per placed rule, and more Step-0 findings that stop work
before it starts. I propose it against my own convenience, and I record that plainly so the DAP is
not weighing an apparently selfless recommendation without the accounting. Neither blocker in this
report is resolved by the rule; it prevents the next one. I propose it; I do not adopt it.

## 7. Dispositions — directed by the DAP at filing

Recorded as directed dispositions, not as builder recommendations. **Both require Architecture
Rev 1.22 before implementation resumes** (§8).

### 7.1 Blocker 1 — Option A: `Genome` gains `tier: ConformanceTier`, inside the signed content

The tier the gate checks against is itself signed and tamper-evident, and a conformance tier is a
genome-level fact — the genome is what BROKKR *is*, and the level it is built to is part of that.

**The three refused options and why**, recorded so the reasoning survives the decision:

- **(B) `tier` on `Cbom`, beside `custody`** — refused: a system-wide conformance property does not
  belong in a *cryptographic-inventory* type. Convenient adjacency is not a modelling argument.
- **(C) a `promote(..., tier, ...)` parameter** — refused, and it is the important refusal: the tier
  would be **caller-supplied and unsigned**, so the party being checked could pass `Baseline` and
  pass the gate. A check whose threshold is chosen by its subject is not a check. This is the same
  structural posture as I-12 (`ClearedContext` cannot be minted by the caller) and the sealed
  `AuthorizedAction` minter — the gate must not take its standard from the thing it gates.
- **(D) read `CapabilityEnvelope.governing_tier`** — refused: the envelope lives in `brokkr-cli`, so
  `brokkr-genome` depending on it **inverts I-5**; and passing it in inherits (C)'s unsigned-input
  weakness unless its signature is separately verified.

### 7.2 Blocker 2 — `KeyRef` is not to be defined; `ExtractionProtection` is simplified

No `KeyRef` type is placed. `ExtractionProtection` is to be simplified so that **no variant requires
a type that does not exist.**

The reasoning, recorded because it is a genuine design judgment and not merely a deletion: **the KEK
reference does not change any tier verdict.** Encrypted-at-rest software custody and plain software
custody both fail R-6.2 (neither is a hardware boundary) and both satisfy R-6.1's declaration
requirement. The field is descriptive detail that does not participate in any predicate, and it does
not earn a new committed type. **If a `KeyRef` is warranted later it will be placed when it serves
more than one field** — which is the same discipline that kept `DesignatedAccountableParty` from
being duplicated (AMD-006 §AMD.0.5) and `RiskAcceptance` from being re-minted for the barrier
(AMD-008 §AMD.0.5).

   in the signed content, and the simplified `ExtractionProtection`. Predicate 7's statement in §6.2
   is corrected from `genome.tier` — currently a reference to a field that does not exist — to the
   field Rev 1.22 places, and §6.11's `ExtractionProtection` is restated without `KeyRef`.
2. **Commit 1 (`brokkr-core` + `brokkr-genome` canonical)** then places, in one revision: the
   `KeyCustody` family, `Cbom.custody`, `Genome.tier`, the `write_cbom_signed` extension, and the
   `genome_signed_content` extension (`brokkr-genome/src/canonical.rs:364`) so the tier is inside the
   genome's signed content as the disposition requires. `Genome::new` gains a parameter — it already
   carries `#[allow(clippy::too_many_arguments)]`, and ~~there are 8 call sites to update~~
   **[CORRECTED — see the CORRECTION annotation appended below, 7 September 2026: the real count is
   two compile_fail doctests, not 8 call sites]**.
3. **Commit 2 (`brokkr-genome`)** then implements predicate 7 against the placed tier, with the tests
   the build instruction specified.
4. **Expected and confirmed consequence, unchanged:** BROKKR's own genome fails predicate 7 — it
   declares Enhanced and holds software keys, so an honest `SoftwareInProcess` declaration is

   is not to be weakened to make fixtures pass.**

**No requirement is relaxed by this report, and R-6.2 remains ABSENT** (Rev 1.21 §13, §14). Nothing
here is progress on the hardware boundary or dual control; it is a correction to the placement of the
third element's mechanism, which remains designed and unbuilt.

## CORRECTION — 7 September 2026 (annotation per §8; original body above is unchanged)

**Directed by:** Jeremy Rose, DAP. **Corrects:** the `Genome::new` call-site count in §8
(Closure path), item 2. The original sentence is preserved above under strikethrough with a
pointer to this section; nothing is rewritten or removed.

**What the report said.** *"`Genome::new` gains a parameter — it already carries
`#[allow(clippy::too_many_arguments)]`, and there are 8 call sites to update."*

**What the count actually was.** **Two** — both `compile_fail` doctests on the `Genome` type in
`brokkr-core/src/genome.rs`. There are no production or test call sites of `Genome::new` anywhere
in the workspace; every other construction is a struct literal, of which there was exactly one
outside the definition (`brokkr-genome/tests/promotion.rs`), and §3 of this report already recorded
that one correctly.

**How the error arose.** The figure came from `grep -rn "Genome::new" --include=*.rs . | wc -l`,
which counts **substring** matches. Three distinct constructors end in the same eleven characters
and were all swept in:

| What matched | What it actually is |
|---|---|
| `DeclaredGenome::new()` (`brokkr-cli/tests/live_model.rs`, `real_integration.rs`) | a test double for the gate's `GenomeResolver` seam |
| `TestGenome::new()` (`brokkr-cli/tests/redteam_13a.rs`) | a red-team fixture builder |
| `Sindri::new(registry, DeclaredGenome::new())` | a gate constructor whose *argument* contains the substring |
| `Genome::new(` in two doc comments (`brokkr-core/src/genome.rs`) | **the only real referents** |

**The shape of the mistake, recorded because it is the report's own subject in miniature.** This
report's §4 finding is *existence is not reachability* — a check that verified a type was defined
without verifying the evaluator could reach it. The call-site count is the same class of error one
level down: **a grep matched a name and was read as having matched a referent.** A substring hit is
not a call site, exactly as a type definition is not a path to an instance. The §5.4 reachability
rule this report proposed would not have caught it — §5.4 governs values a rule evaluates, not
counts quoted in prose — so it is recorded here as a distinct instance rather than folded into that
finding.

**How it was found.** During implementation at commit `a8900b8`, when adding the `tier` parameter
made the compiler enumerate the real call sites. `cargo build --workspace --all-targets` reported
two errors, both struct-literal field omissions, and no arity errors at all — which is what a
zero-call-site function produces. The builder then re-ran the grep, read the matches, and reported
the correction in the same turn as the implementation.

**Effect on the report.** None beyond the count. The closure path in §8 is otherwise unchanged and
was followed as written; both doctests were updated for the new arity at `a8900b8`, and **a third
was added** proving `tier` is a required field, so a genome declaring no conformance level is
unrepresentable. The blockers in §2 and §3, the root cause in §4, the proposed rule in §5, the
buildability determination in §6, and the dispositions in §7 are unaffected.

— End of correction, GAP-2026-09-07-001.
